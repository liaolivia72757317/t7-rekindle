# 战斗动作时间轴调查：静态阶段

调查日期：2026-10-13。范围：角色 `110001`、主武器 `1030411`（分类 `32`）的四方向普通攻击与招架；冲刺攻击、换武器仅作为时长同步链的对照。

## 结论

**已确认表内时长、原始动画时长、当前服务端计时器和动画图参数并非同一组数值；现有证据尚不足以认定客户端表是旧版本。**

当前实现存在更直接、可复核的差异：

- 普通攻击的阶段计时器采用表内基准值的代码常量，但同步报文的 `state_time_ms` 为 `0`。
- 普通攻击的动画节点绑定了 `BattleStateDuration → enforcedDuration`，并非只有冲刺攻击支持消息时长。
- 主武器被招架、碰撞反弹复用普通收招时长，没有采用表内对应的专用时长。
- 招架预备、成功反馈的计时器为 `0`，松键直接回空闲；资源中则有独立的预备、成功和释放状态。

这些事实足以要求重新核对“如何使用配置”，但尚未证明哪组数值符合原服。当前代码的选择和通过的单元测试，不作为原服行为证据。

## 1. 取值与消费链

```text
s_weapon_cli：武器 → 分类
  ├─ s_battle_param_cli：参数组 / 键前缀 / 分类 / 动作 / 模式 → 参数
  └─ character：动画别名 → 动画资源、behavior

本项目 battle.py 阶段计时器
  → STATE_SYNC / STATE_SYNC_SIMPLE
  → 客户端状态应用
  → 先应用状态属性，再写 BattleStateDuration = 消息时长 / 1000
  → behavior 中绑定 enforcedDuration 的动画节点

下一条状态消息、动画图转换及输入处理共同影响可见动作和恢复时点。
```

原生静态样本显示，状态应用会写入消息携带的时长，取值为 `0` 时也进入该写入路径。因此，动画图中保存的默认时长不宜直接视为运行时最终值。`enforcedDuration=0` 在所选节点上的最终播放行为，仍需补充验证。

`s_act_state_cli` 的攻击阶段时长字段分别包含 `-11002`、`-11003`、`-11004`、`-11005`；这些不是可直接计时的负毫秒。已检查的字面时长访问器会将负值转为 `0`，但尚未闭合这些标识在普通攻击中的完整解析路径。

### 文件与选行检查

- 在本次检查的四个 VFS 包中，目标三张表只出现在 `data1.vfs`；对应相对路径未发现散文件。
- 参数表的原生键是五个 16 位字段。本次攻击完整键为 `(2, 0, 32, direction, 2)`，方向值为上 `1`、右 `4`、下 `2`、左 `3`，四行均唯一。
- 表中其他分类存在重复完整键；状态表也存在同 ID 多行。诊断提取保留行号和键，不采用“找到首个同 ID 行”的通用规则。
- 已观察到的参数字符串查询路径按武器分类选值，并有分类 `0` 的回退；该路径使用参数组 `6`，不等于已经证明普通攻击直接使用参数组 `2` 的时长。

以上文件检查未发现另一份覆盖表，但不覆盖运行时内存修改、远端修正或原服配置版本。

## 2. 普通攻击：表、动画与当前计时器

下表单位均为 ms，原始动画时长四舍五入到整数。三元组依次为 **预备／过程／结束**，不含按键维持阶段。

| 方向 | 表内基准时长 | 当前阶段计时器 | 原始动画时长 |
| --- | --- | --- | --- |
| 上 | 360 / 640 / 500 | 360 / 640 / 500 | 300 / 600 / 533 |
| 右 | 360 / 640 / 500 | 360 / 640 / 500 | 300 / 567 / 533 |
| 下 | 400 / 700 / 400 | 400 / 700 / 400 | 367 / 600 / 467 |
| 左 | 360 / 640 / 530 | 360 / 640 / 530 | 333 / 567 / 500 |

复核入口：`s_battle_param_cli` 的 `[持续时间]预备/过程/结束`，以及所选 character 中的 `Attack{Up,Right,Down,Left}{Prepare,Process,Finish}` 别名。

所有方向的 `Prepare / Process / Finish / Parryed` 节点都绑定 `enforcedDuration`。预备节点还保存了上 `420`、右 `400`、下 `470`、左 `400` ms 的默认值；它们既不等于表值，也不等于原始 clip 时长，且会受变量绑定影响。

`Attack*Hold` 的原始 clip 均为 `1000` ms，节点采用循环模式；当前逻辑等待松键而非固定 `1000` ms 到期。这个例子直接说明：**clip 长度不等于状态持续时间。**

当前普通攻击报文时长为 `0`，服务端仍按上表的固定计时器发送下一阶段状态。因此应分别测量动画进度与状态推进；仅凭两组静态数值不足以判断实际播放速度或手感差异的大小。

`reactionMs()` 对主武器返回普通攻击结束阶段时长；`terrain=True` 没有改变这个分支。徒手使用独立反应表，是不同分支。这里确认的是当前实现与资源的差异，不是直接决定应替换为哪一列。

### 防守方招架

| 环节 | 状态表 | 原始资源 / 动画图 | 当前实现 |
| --- | --- | --- | --- |
| 预备，状态 305–308 | 150 ms | 预备别名与保持别名引用同一组 2667 ms clip；预备节点绑定时长变量 | 计时器 0，随后发送保持状态 |
| 保持，状态 223–226 | 0 | 保持节点循环 | 等待松键或其他状态 |
| 成功，状态 231–234 | 667 ms | 四方向 clip 均为 600 ms；成功节点没有 `enforcedDuration` 绑定 | 计时器 0，随后恢复保持或空闲 |
| 释放，状态 227–230 | 400 ms | 动画图存在 `ParryRelease` 事件转换 | 松键直接回空闲，跳过释放状态 |

`0` ms 计时器表示不额外安排等待，不代表成功动作在屏幕上恰好显示 `0` ms；消息处理、帧更新和混合转换仍影响可见结果。成功节点没有时长绑定，也意味着仅改变消息时长未必会缩放该 clip。

## 4. 其他时间轴不要混在一起

- **判定窗口**：当前普通攻击接触判定覆盖过程阶段；所选表行的 `[碰撞时间]开始/结束` 均为 `0`。这两个 `0` 的原生语义尚未闭合，不应据此将判定窗口清零。
- **输入恢复**：表内有“忽略消息起始／截止时间”等字段，例如上方向技能为 `249.6–640` ms；当前恢复打断和输入缓冲由业务状态机实现，并非逐项执行这些表字段。
- **冲刺对照**：该武器的冲刺状态 `439` 使用动作类型 `13`，原始表过程时长为 `1200` ms，原始 clip 为 `1333` ms；动作类型 `32` 下的 `2033` ms 属于战技，不是冲刺参数。当前静态表按实际动画有效时长同步完整过程，动画解析不可用时才使用冲刺表时长；该时长策略不作为原服行为结论。
- **动画裁剪**：冲刺被招架节点还包含约 `133` ms 的尾部裁剪。比较“原始长度”和“可见时长”时必须保留裁剪、混合与状态中断信息。

## 6. 后续实测矩阵

恢复独立诊断会话后，先固定武器、角色、帧率、按键持续时间和无加成条件；每个条件至少重复 5 次。变更只用于诊断副本，每组结束还原基线。

| 实验 | 唯一改动 | 要区分的问题 |
| --- | --- | --- |
| 基线 | 不改参数 | 消息、动画、判定、恢复四条时间轴分别是什么 |
| 资源对照 | 选定表字段 ×1.5，业务常量与消息保持不变 | 客户端是否实际消费该字段 |
| 消息对照 | `state_time_ms` 分别取 0、表值、原始 clip 时长，阶段计时器不变 | 消息是否控制播放比例；下一状态是否提前截断 |
| 阶段对照 | 只调整一个阶段计时器，消息保持不变 | 下一状态、判定与输入恢复是否随之移动 |
| 招架对照 | 分别改变预备、成功反馈等待时间，不同时改变消息时长 | 反馈动作是否被后续状态覆盖；成功节点无时长绑定的影响 |

每次记录：输入时刻、状态 ID / 序号、消息时长、客户端状态应用、动画局部时间 / 结束、判定窗口、首次接受下一动作的时刻。先分轴归因，再决定是否修改时长来源；不把所有数值统一替换成表值或动画长度。
