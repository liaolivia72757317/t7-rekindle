# Rust 中心游戏服务

## 目标与入口

启动器填写服务器 IP 或域名、端口，使用当前昵称自动领取游客票据并启动原客户端。创建、刷新、加入、准备、开始和离场均在游戏大厅操作。云端游戏服务是独立 Rust 进程，不依赖 Java 账号服务，也不使用 P2P 或 SSH 隧道传输游戏消息。

游客接入不验证昵称所有权，不提供账号存档；角色和装备沿用当前公共配置。同名玩家拥有独立连接身份与战斗对象，不能因为昵称相同控制对方。

## 分层与所有权

| 模块 | 职责 |
| --- | --- |
| Desktop | 服务器配置、游客票据申请、正常启动与清理；不拥有房间连接或比赛阶段 |
| C++ Runtime | 原客户端适配、原生采样、WinHTTP WSS 连接与事务提交 |
| Business 联机模块 | 原版协议与 Rust 协议转换、冻结角色映射、远端显示插值；不裁决伤害 |
| Rust transport | HTTP/TLS/WS 接入、有界队列、限流、请求关联与断线通知 |
| Rust auth | 短期游客票据签发、一次性兑换与连接身份绑定 |
| Rust lobby / room | 房间目录、成员、房主、准备、加载、倒计时和对局阶段 |
| Rust battle / motion / combat | 动作期限、位移校验与广播、命中、格挡、血量、死亡、复活与计分 |

本地人机模式保留原来的独立裁决；启动时选择模式，同一对局不会同时运行本地与 Rust 两套伤害裁决。

## Rust 结构

当前为模块化单进程服务。Axum 提供 HTTP/WebSocket，Tokio 管理异步连接和定时器；网络任务通过有界消息队列交给协调器。协调器拥有大厅与房间状态，顺序处理修改，业务模块不持有 socket。慢连接输出拥塞会断开，避免阻塞其他房间。

`Room<Waiting>`、`Room<Loading>`、`Room<Countdown>`、`Room<Running>` 通过消费旧状态完成类型转换。Running 组合动作、位移与战斗模块；协议层只发布状态快照，不暴露内部可变对象。角色、对象、房间目录编号使用不同类型，连接身份不等同战斗 RID。

公共限制与 `RoomRules` 在 `game-server/src/limits.rs`。部署参数通过命令行和 systemd 环境配置输入；服务器地址、证书和地图目录不写死在源代码中。当前协调器尚未按房间分片，扩展吞吐前需要测量每房间的广播与适配成本。

## 连接与阶段

1. 启动器 HTTPS 请求游客票据，保存供本次原生连接读取的 Windows 用户保护数据。
2. 原客户端逻辑连接对应唯一 WSS 网关。票据只兑换一次，Hello 身份与昵称必须匹配；Python 不接触票据。
3. 大厅请求经网关操作 Rust 房间。房主可单人开始；多人时其他成员准备且双方阵营都有成员。
4. Rust 冻结成员并为每个接收端生成角色映射。客户端真正加载、选角、参战后回报 Loaded。
5. 全员加载完成后统一倒计时与 Running。动作、位移和接触继续走同一网关连接。
6. 离场、断线或加载超时由 Rust 清理成员与阶段，适配器执行原客户端离场流程。

网关按 FIFO 发送，最多八个请求同时等待回复；Python 状态与输出提交成功后才确认回复。每个请求有独立期限，失败或结果不确定时断开，不重放建房、加入或攻击。

## 多人模型

单人、双人与多人统一使用冻结的 `peers` 列表和按角色分配的位移缓冲。原客户端采样上限为 20 个角色槽位：本机 RID 1，敌人 2–11，队友 12–20。每个接收端的映射不同，共享角色编号保持不变。部署可配置 1–20 人；超过此范围需先扩展客户端适配与采样能力。

服务端按连接身份推导操作角色，拒绝未知角色、过期对局、序列重放与队友伤害。当前接触校验仍基于客户端物理报告和粗几何约束，不是完整服务端物理或可靠反作弊。
