# 目标架构

T7R 由 Java 平台服务器、Rust 战斗服、WPF 启动器和原游戏客户端四类实体组成。原客户端统一连接本机兼容网关，平台业务按游玩模式选择本地或 Java 后端，战局业务统一交给 Rust。

本文定义目标职责和接口边界，不表示相关能力已全部交付。当前启动路径见[架构说明](../architecture.md)，迁移进度见 [Rust 运行时迁移](rust-runtime-migration.md)，联机接入见[三模式实施计划](battle-network-v1.md)。

## 当前生产边界

启动器及无界面宿主已统一采用 Rust，产品不链接或分发 Python；开发对照移至 `tests/reference`。NativeBridge 仅负责客户端生命周期、原生证据和表现适配。平台身份、配置、存档仍由现有 C# 后端提供，称号归属仍由账号服务决定，Rust 负责原协议转换。

这次切换没有完成共享房间、独立 MatchHost、公共契约 v2／ABI 2 或战斗输出调度解耦。当前仍由网关持有单场战局、C# 泵消费战斗输出；LAN 和 Linux 节点按下述目标继续实现。

## 实体职责

| 实体 | 职责 | 边界 |
| --- | --- | --- |
| Java 平台服务器 | 在线账号、大厅、公告、用户配置、物品与称号归属、房间、战斗节点调度和结果持久化 | 不执行实时战斗，不转发高频战斗数据 |
| Rust 战斗服 | 比赛状态与时钟、AI、动作、伤害、防御、死亡、复活、计分和胜负 | 不操作原客户端进程，不承担平台账户业务 |
| WPF 启动器 | 界面、客户端生命周期、兼容网关、后端路由、本地平台服务及世界采样适配 | 不另行维护一套战斗规则；业务模块独立于 WPF 界面 |
| 原游戏客户端 | 输入、渲染、动画，以及本期所需的移动和碰撞事实生成 | 平台身份和最终战斗结果由对应后端决定 |

## 游玩模式

启动器支持离线和在线两种模式；离线模式包含本地人机和 LAN 对战。

| 场景 | 大厅与配置 | 房间管理 | 战斗运行位置 |
| --- | --- | --- | --- |
| 离线人机 | 本地平台服务 | 本地平台服务 | 本机启动器进程内的 Rust |
| LAN 房主 | 本地平台服务 | 房主本地平台服务 | 房主启动器进程内的 Rust |
| LAN 加入者 | 本地配置及房主提供的信息 | 房主本地平台服务 | 连接房主的同一 Rust 战局 |
| 在线对战 | Java | Java | 分配的 Linux Rust 节点 |

LAN 加入者不另外创建战局。房主本人也按统一战斗接入语义参与，各客户端共享同一份比赛状态。

账号在线状态与游玩模式分离：登录账号不强制进入在线对战；离线人机和 LAN 不依赖 Java。离线配置与在线配置分别维护，不自动用本地存档覆盖平台数据，本地或 LAN 结果不直接产生在线奖励。

房间与比赛分开管理。一个 `roomId` 可以先后产生多个 `matchId`；比赛结束后按房间规则返回准备状态，而不是把比赛状态当成房间的永久状态。

## 启动器的统一客户端入口

原客户端始终连接本机兼容网关，不感知平台后端或战斗服的实现与部署位置。网关识别业务含义后路由，不将原协议的 `login`、`logic`、`instance` 通道直接固定对应到 Java 或 Rust。

| 模块 | 输入与输出 |
| --- | --- |
| 客户端生命周期 | 检查客户端版本，创建受管理进程，安装运行时适配，结束并清理资源 |
| 客户端兼容网关 | 处理原协议握手和编解码；将请求转换为平台操作或战斗输入，将后端响应及事件转换为原协议消息 |
| 平台业务接入 | 统一大厅、配置和房间等操作，选择本地服务或 Java API |
| 战斗业务接入 | 统一准入、输入和事件语义，连接进程内 Rust、LAN 房主或远端节点 |
| 世界采样适配 | 按本局权威模式采集本机世界观测，转换角色标识、时钟和批次，不自行生成最终战斗结果 |

原协议握手、平台登录和战局准入是不同步骤；原游戏心跳、平台在线租约和战局存活检测也分别维护。原协议连接成功不等于拥有平台身份或房间资格。

本地平台服务既处理明确的固定响应，也维护阵容、装备配置、房间成员、准备和退出等动态状态。未实现功能使用明确的失败或空数据语义，不以固定成功响应代替实际业务。

兼容网关使用 Rust；本地平台服务及 Java 接入使用 C#，通过独立于界面的 `IPlatformBackend` 统一业务语义。跨语言平台请求异步处理，携带请求标识与会话代次；退出或切换账号后，旧响应不覆盖新状态。

## Rust 共用核心与部署

本地和远端使用同一套战斗核心源码、同一发布版本及相同输入输出语义，按目标平台分别构建，不要求 Windows 与 Linux 共用一个二进制文件。

| 平台 | 宿主形式 | 依赖边界 |
| --- | --- | --- |
| Windows x64 | Rust 库通过 NativeBridge 的 C ABI 接入，运行于启动器进程内；可沿用 `staticlib` 链入 NativeBridge 的方式 | 不增加玩家可见的战斗服务进程，UI 不执行战斗循环 |
| Linux | 原生 Rust 服务端程序，运行同一战斗核心和运行时 | 不加载 WPF、Windows NativeBridge 或嵌入式 Python |

战斗核心不依赖 Windows API、原客户端内存布局或原协议对象。客户端进程适配留在 Windows 侧；两种宿主需要的规则和资源数据采用明确的跨平台输入，不依赖某个玩家的本地文件路径。原客户端及资源仍不随项目分发。

两端统一加载离线导出的版本化 JSON 战斗数据包。Windows 目标是在资源预检阶段透明生成或加载本地缓存，Linux 加载部署者准备的数据包；开战后固定使用该资源快照。当前导出和预检入口见[公共契约](../battle-contracts.md)。

Linux 节点单进程支持多场比赛，各局独立状态、串行事件队列和计时器，不同比赛并行执行，共享只读资源。预留与运行中的比赛均计入节点容量。战斗连接使用节点内建 TLS，节点访问 Java 使用 HTTPS；采用锁版的 tokio-rustls、reqwest 及必要配套依赖。

进程内 FFI 与远端网络接入遵循相同的业务校验、事件顺序、状态转换和结果语义。本机调用不必经过 TCP，但也不跳过必要的身份归属和输入校验。

FFI 使用固定宽度字段、明确所有权的缓冲区和错误码，不传递跨语言容器，不允许异常跨界。宿主同步停止并等待工作线程退出后，再释放相关资源。战局状态常驻，输入队列有界，避免逐事件全量复制；性能以固定负载下的处理与排队时延验证，不以语言选择代替验收。

## 战斗权威模式

### 本期范围

本期采用客户端采样、Rust 裁决。Rust 不自行模拟移动和碰撞，也不补建客户端物理事实的真实性校验；仍检查消息结构、来源归属、时间与序号、去重及比赛隔离。

每个人类角色由所属客户端采样，AI 由比赛指定的客户端执行物理并采样。Rust 产生 AI 决策和动作意图，消费世界观测并计算伤害、防御、死亡、复活及最终结果。采样职责分配与退出规则见[三模式实施计划](battle-network-v1.md#职责)。

### 后续模式的兼容边界

| 项目 | 本期客户端采样模式 | 后续服务端模拟模式 |
| --- | --- | --- |
| 玩家意图 | 必需输入 | 必需输入 |
| 移动与碰撞事实 | 来自指定客户端的观测 | 来自服务端模拟 |
| 客户端世界观测 | 必需的规则输入 | 按能力声明选用，不天然具有权威性 |
| AI 位移 | Rust 决策，指定客户端执行物理 | 服务端推进 |
| 客户端表现 | 本地物理执行与采样上报 | 接受权威状态，按需配合预测、插值和纠正 |
| 最终战斗结果 | 战斗服裁决 | 战斗服裁决 |

权威模式由服务器能力、房间要求和客户端兼容能力匹配，在准入及开局时确定并绑定 `matchId`，局内固定。能力不匹配时拒绝准入，不静默降级，不由客户端自行切换。

不同战斗服实现通过同一公共契约接入，按能力、规则和资源版本区分，不在启动器中按实现名称编写专用业务分支。协议兼容不代表规则或信任等级相同。

客户端离线移动接管、AI 本地物理驱动和位置同步屏蔽等适配按权威模式启用。后续模式还需实现权威位置同步与纠正；协议预留不表示客户端适配已就绪。本期只实现客户端采样模式，不提前实现服务端物理模拟。

## 协议与数据契约

### 四条接口边界

| 边界 | 契约范围 |
| --- | --- |
| 原客户端与兼容网关 | 原协议行为、兼容版本、身份和 RID 映射、运行时适配 |
| 启动器与平台服务 | 账号、大厅、配置、房间操作、错误及事件通知；在线后端通过 Java API 接入 |
| 启动器与战斗服 | 准入、玩家输入、所需世界观测、状态与战斗事件；本机 FFI 和远端传输共用业务语义 |
| Java 与战斗节点 | 注册、能力声明、租约、分配、比赛生命周期和结果提交 |

现有 BattleProtocol v1 的帧传输和 `GameData` 中继是接入基础，原协议字节流不替代公共战斗语义。战斗核心消费有明确含义的输入并输出状态和事件，由兼容网关转换为原游戏协议。精确消息体、错误码和编码规则由协议实现配套定义。

公共战斗消息体采用明确的二进制格式，沿用现有帧结构与编号；平台 API 和资源数据包使用 JSON。已实现的准入消息体及 C#／Rust 一致性语料见[公共契约](../battle-contracts.md#帧与准入)。

### 战斗输入与输出

| 数据 | 必须表达的内容 |
| --- | --- |
| 能力与准入 | 协议版本、权威模式、地图、规则与资源兼容要求、已分配身份及房间绑定 |
| 比赛配置 | 房间与比赛标识、成员、角色、阵营、装备和规则快照 |
| 玩家意图 | 输入序号、时序信息、移动按键、朝向输入、攻击、格挡等操作 |
| 世界观测 | 来源、所属角色、采样时间、实体生命代次、批次号、位姿、速度、地形与刀刃接触证据 |
| 权威状态与事件 | 比赛时间、状态版本、认可的位姿与动作、属性、出生、死亡及战斗反馈 |
| 比赛结果 | 正常结束或中止、最终比分、玩家统计和用于幂等提交的结果标识 |

玩家意图表示期望操作，世界观测表示客户端观察到的事实，权威结果表示战斗服最终决定；三者不混用。后续实现可根据自身模拟验证、替代或忽略相应观测，不将客户端上报接触固定为唯一伤害来源。

协议同时约定坐标系、单位、时钟映射、输入确认、批次顺序、重复与迟到消息处理，以及旧比赛和旧生命事件的隔离。状态快照、增量和一次性事件分别定义，不靠传输分段推断业务边界。

`accountId`、`playerId`、`actorId`、传输连接 ID 与原客户端 RID 各有独立含义。每个原客户端把自己视为 RID `1` 的约定由网关映射，Rust 使用比赛内统一角色标识；目标引用、观测、出生和结算中的角色引用同步转换。旧游戏 AUTH 和固定本地用户 ID 不作为平台认证依据。

## Java 数据权威与战局生命周期

Java 维护平台持久数据、在线房间和调度信息，不维护每帧动作、血量、AI 或碰撞状态。运行中的战局状态由 Rust 维护，战后持久战绩和奖励由 Java 根据可信节点提交的结果处理。

1. 平台或本地房间服务确认成员、阵营和配置，为新比赛生成独立标识及配置快照。
2. 在线模式由 Java 分配节点并下发地址与准入信息；启动器直接连接战斗节点，实时数据不绕行 Java。
3. 战斗服运行期间使用已确认的配置，不逐次向 Java 查询角色装备或账户资料。
4. 在线战斗结束后向 Java 提交结果，按比赛和结果标识幂等处理，重试不重复结算；离线结果留在本地，不作为在线奖励依据。
5. 返回房间后按规则再次准备，新比赛不复用上一局的事件和计时器。

节点凭据与用户登录凭证分离，普通启动器不注册为在线节点。Java 短暂中断不直接终止已开始的战斗，结果保留并重试；本地、LAN 和在线退出规则分别处理，不把网络故障自动切换成一场新的离线战局。

## 客户端文件与运行时适配

原客户端程序、DLL 和资源包保持不变；社区兼容逻辑只在运行时内存中适配，按受支持版本验证后安装。签名或资源结构不匹配时停止适配，不转为修改磁盘程序或资源。

允许按用户操作修改 `UserData.cfg` 等明确支持的用户配置。只更新对应字段，保留其他内容，执行冲突检查与备份，不扩大为任意客户端文件写入。现有画面和声音配置保存规则见[运行契约](../runtime-contracts.md#游戏配置文件与模式切换)。

启动器设置、平台凭证、离线存档及日志保存在启动器自己的用户数据目录。不同模式复用客户端兼容层，不随战斗服实现改变原始资源文件。

## 实施边界

共享战局的下一实施边界为：平台拥有稳定房间和不可变开局快照，`MatchHost` 拥有单场战局及独立参与者输出队列，网关只保留原协议连接、RID／原生实体映射和战局连接。普通参与者退出移除其角色与水位等待，AI 采样所有者退出中止比赛；WPF 通过窄客户端生命周期接口调用 UI 无关的会话编排。该边界尚未落地，当前已完成的输入时间校验、空接触状态发布优化及 FFI 注册表锁隔离见 [Rust 迁移进度](rust-runtime-migration.md#架构优化增量)。

后续统一升级业务契约为 v2、Rust 开发 FFI 为 ABI 2，不保留旧开发版本解析或包装；帧传输布局保持不变。公共引用使用 `actorId`／`lifeId`，首次生命为 1，创建新生命时递增。两端各自 RID 1、不同原生实体、直接调用与序列化往返使用相同业务验证入口，并以合成共享战局验收；LAN 发现、联机界面、跨机校时和远端节点不属于这一实施边界。

当前生产启动路径使用 Rust 和 C++ 客户端适配，独立宿主仍为 Windows .NET 控制台；它们不是 Linux Rust 节点。Rust 模块基础也不代表多人战局已经接通。

总体目标为单机、LAN、在线三模式闭环，复用现有账号、公告、名称和称号。当前实施先完成离线单机与 LAN；Java 在线平台、在线调度、节点准入及结果提交留待后续。完整商城、服务端物理模拟、局内加入、断线重连与 AI 采样者迁移不纳入本期。

| 里程碑 | 交付与验收关卡 |
| --- | --- |
| M0 契约与基线 | 公共消息、资源格式与跨语言语料；补齐存档回放、真实世界事件及性能基线 |
| M1 网关与本地平台 | Rust 网关、C# 本地平台、资源加载及 FFI 生命周期；完成预检、大厅、配置和退出 |
| M2 Rust 单机 | 迁移原规则、AI 与导航；1 玩家加 19 AI 通过回放、存档及性能关卡 |
| M3 共享战局与 Linux | 多来源采样、角色映射与多局宿主；两真实客户端完成互相攻击、复活、结算及重开，跨局状态隔离 |
| M4 LAN | 房主房间、发现与手工地址、准备及退出；断开互联网后完成整局 |
| M5 在线 | Java 配置、房间、调度、准入与结果重试；至少两个节点通过容量竞争与故障验证 |
| M6 产品切换 | Windows／Linux CI、安装、包清单与部署文档；Windows 默认 Rust 与生产 Python 移除已完成；其余关卡独立验收 |

M3 实机通过前不开展大规模 Java 和联机界面接入。升级通过结束会话后整包替换，不迁移运行中的战局；保留已有 ABI、存档和设置格式。首期在线持久化战绩，不新增奖励经济规则。

当前顺序为 M0／M1 剩余项 → M2 → M3 中离线多人共享战局 → M4。Linux 远端宿主、M5 及 M6 中的远端部署项延期；共享协议和跨平台核心继续保留既定边界。暂缓项不记作验收通过，安装升级和远端交付仍需满足相应关卡。

2026-10-16，Windows 隔离开发路径已完成 1 名玩家＋19 名电脑的连续两局自然结算、回房重开及正常停机，单机常规功能闭环验收通过，详见 [Rust 迁移验收记录](rust-runtime-migration.md#单机功能闭环验收记录)。这不替代 M0／M2 的完整回放与性能关卡；性能按专项后续推进，LAN 双客户端及安装升级尚未验收。
