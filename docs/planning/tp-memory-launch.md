# TP 纯内存启动：验证与实施方案

验证日期：2026-10-02。

## 结论

**纯内存启动已实现并接入 Bootstrap；原版客户端已自动进入大厅，匹配后进入战局的验收已通过。已观察完整进程树中没有已知 TP 模块，驱动全程跟踪及其余游戏内功能验收仍待完成。**

实施方式为：从原版文件只读恢复游戏映像，在首次恢复主线程前完成主程序适配；必要 DLL 则在重定位完成、入口执行前完成适配。真实会话已自动连接本地登录与逻辑服务，接收登录及同步响应，并进入“战场”大厅；全程没有手动输入账号或操作游戏窗口。

目标与约束：

- 支持[当前原版客户端基线](../requirements.md#客户端兼容性)，不要求用户换用派生 EXE。
- 适配只改变内存，不替换、删除或修补客户端目录中的文件，包括 `TesSafe.sys`。
- 不先运行 TP 再终止它；不以短暂启动 TP 换取解包结果。
- 产品不包含游戏代码捕获、内存转储或派生客户端二进制。
- 任何准备失败都结束本次拥有的挂起进程，不自动回退到原保护链。

自动进入大厅和匹配后进入战局的验收已通过；仅显示登录界面或收到协议响应均不算通过。剩余验收包括移动、游戏内退出、再次启动和驱动全程跟踪。

## 已完成的验证

### 原版文件只读检查

输入主程序 SHA-256 与当前支持基线一致。检查使用 `SEC_IMAGE_NO_EXECUTE` 映像映射，没有启动游戏或加载其依赖 DLL，检查前后主程序哈希一致。

| 检查项 | 本次结果 | 对实施的影响 |
| --- | --- | --- |
| 原入口 | 位于 `.tp3` 节区 | 保留原入口直接恢复主线程会进入保护层 |
| 静态导入 | 包含 `TieJiClientBase.dll` | 处理范围包括系统装载器解析的依赖，不只是游戏入口 |
| 导入目录 | RVA 非零，Size 为 0，存在有效 descriptor | 检查器需要按支持基线和映像边界解析，Size 为 0 不等于没有导入 |
| EXE TLS callbacks | 当前静态表为零项 | 不代表依赖 DLL 没有早期初始化；TLS 数据初始化仍须保留 |
| 六处 TPFree 代码签名 | 初始映像全部不匹配，参考解包映像全部匹配 | 这些补丁依赖解包后的代码，直接提前应用不成立 |
| 游戏 CRT 入口签名 | 初始映像不匹配，参考解包映像匹配 | 仅把入口地址改向原游戏入口不充分 |
| 两段代码对比 | 共 24,072,192 bytes，其中 22,499,101 bytes 不同 | 初始映像与可运行代码不是相同内容；差异计数本身不说明具体编码算法 |

参考解包映像只用于诊断比对，不是产品运行输入。下面的独立解码实现只读取原版文件。

### 独立代码恢复

[Ap32](../../src/Runtime/launcher/Ap32.cpp) 实现数据解码，[ClientCode](../../src/Runtime/launcher/ClientCode.cpp) 将其用于绑定 SHA-256 的原版主程序。没有新增生产依赖，也不加载或执行输入 EXE/DLL。

- 第一段代码由 184 个连续 AP32 块组成，第二段有 1 个 AP32 块。
- 共 185 块的压缩数据 CRC、解压长度、解压数据 CRC 均通过；检查区段尾部填充后，仅在内存中补齐映像布局。
- 恢复的第一段代码为 24,018,944 bytes；与参考映像只有已有启动返回值适配的 2 bytes 不同。第二段为 53,248 bytes，与参考映像完全相同。
- 对参考中的这处已知启动适配还原后，两段代码逐字节相同。独立 C++ 验证运行的恢复用时为 218 ms，此值不是游戏启动性能承诺。
- 原文件哈希不变，中途取消测试通过。实现不输出解包后的客户端文件，也不依赖参考映像、转储或历史运行地址。

[合成测试](../../tests/cpp/Ap32Tests.cpp) 覆盖 literal、零字节、短距离、长距离、重复距离、重叠复制、距离阈值、分块消费，以及截断、CRC 错误、长度/距离溢出和越界拒绝。[基线测试](../../tests/cpp/ClientCodeTests.cpp) 覆盖未知输入及取消。原生测试、NativeBridge 构建及 17 项构建/布局 Python 测试通过。

### 导入、数据和内存映像

[ClientImports](../../src/Runtime/launcher/ClientImports.cpp) 按固定名字重建 19 个模块的 794 个导入，不使用历史运行地址。只读导出检查未发现缺失名称，实际启动也已通过系统装载器解析。名字存在和启动成功不等于所有游戏功能调用都已覆盖。

进战局资源读取使用的导入槽应绑定 [`D3DXCreateBuffer`](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dxcreatebuffer)，其首参数为缓冲区长度；误绑到 [`D3DXGetShaderConstantTable`](https://learn.microsoft.com/en-us/windows/win32/direct3d9/d3dxgetshaderconstanttable) 会把长度当作指针读取。[导入回归测试](../../tests/cpp/ClientImportsTests.cpp) 分别锁定这两个函数的导入槽，修正缓冲区创建绑定，并保留真正的着色器常量表读取绑定。

[ClientImage](../../src/Runtime/launcher/ClientImage.cpp) 生成 62,210,048 bytes 的内存映像，保留原版初始化数据、TLS 和资源，BSS 保持零初始化；旧装载器区域仅保留新导入数据。当前基线无 ASLR/重定位目录，要求原固定映像基址。

[RemoteImage](../../src/Runtime/launcher/RemoteImage.cpp) 已在真实原版挂起进程中完成全部映像写入和逐字节回读，8 个内存区域的页保护及 WOW64 启动入口上下文检查通过。该项测试始终没有恢复主线程，最后结束拥有的进程；磁盘主程序哈希不变。

### 自建 x86 启动实验

在 Windows x64 上编译自建 x86 EXE 和测试 DLL，启用 `/W4 /WX`。测试 DLL 在 `DLL_PROCESS_ATTACH` 写入测试目录中的标记；EXE 有原入口和备用入口，分别以 `41`、`42` 退出。所有修改仅发生在本次创建的挂起进程内。

| 用例 | 退出码 | 测试 DLL 初始化 | 结果 |
| --- | --- | --- | --- |
| 挂起后直接恢复 | 41 | 是 | 对照通过 |
| 只修改内存 PE 入口字段 | 41 | 是 | 本次环境中，修改头部未改变实际启动入口 |
| 修改入口字段及 WOW64 启动上下文 | 42 | 是 | 入口重定向成功，但依赖仍先初始化 |
| 同时移除测试 DLL 的内存导入 descriptor | 42 | 否 | 验证了首次恢复前阻断该静态依赖的机制 |

四组结果均符合预期，测试子进程全部退出，测试 EXE/DLL 的磁盘哈希不变。

该实验只证明所覆盖的装载时序和内存修改机制，不证明真实客户端的解包、动态依赖、图形初始化或游戏兼容性。

### 必要 DLL 的初始化时序

自建 EXE 与 DLL 使用相同首选基址，强制 DLL 重定位。DLL 的初始化逻辑写入标记，导出函数返回固定结果。

| 用例 | 加载事件时重定位完成 | 入口断点时重定位完成 | 初始化标记 | 导出调用 |
| --- | --- | --- | --- | --- |
| 对照 | 否 | 未设断点 | 存在 | 正常 |
| 入口断点观察后放行 | 否 | 是 | 存在 | 正常 |
| 入口断点处修改含重定位字段的指令 | 否 | 是 | 不存在 | 正常 |

三组测试的文件均未修改，进程全部退出。结果支持在 `LOAD_DLL_DEBUG_EVENT` 设置入口断点、在入口断点处实施依赖适配；直接在加载事件中覆盖尚待重定位的字段会选错时机。

[DebugClient](../../src/Runtime/launcher/DebugClient.cpp) 将创建进程与调试事件循环放在同一专用线程，按 PID 持续记录加载和退出事件。原版 `TenProxy.dll` 没有 TLS 初始化，已验证其入口处适配成功；它仍作为协议依赖使用，没有整体屏蔽。卸载时移除入口记录，重新加载时重新验证。已知 TP 模块或未验证的子进程到达加载/创建事件时，结束本次 Job 内进程，再释放事件，不回退原入口。

大厅使用的 `TieJiWebHelper.exe` 是原客户端的 CEF 网页组件。创建事件必须同时匹配原版目录路径、SHA-256 和本次 Job 归属，才允许执行；其后代同样验证，模块、入口断点及初始异常状态按进程隔离。主程序退出或会话停止时清理整个拥有的进程树，不因组件同名而放行。

[ClientAdaptation](../../src/Runtime/launcher/ClientAdaptation.cpp) 包含主程序 15 项内存变更和必要 DLL 的 16 项变更，覆盖调用路径及对应动态名字。签名、范围和重叠检查先于写入；必要 DLL 的绝对操作数按实际加载地址校验。

主程序中包含 `TCLS` 的行为树注册名称必须保留。清除这些名称会破坏自动登录，而不是移除加载路径；已移除这项清除操作，并增加名称保留回归测试。

组件验证还覆盖主程序身份不符、DLL 入口签名不符、准备失败和取消。自建 GUI 进程树测试覆盖子孙进程正常运行、未知子进程、路径不符、哈希不符，以及运行中停止后的整树清理；拒绝用例确认子进程尚未执行测试入口。原生测试、NativeBridge/RuntimeTests 构建及 21 项相关 Python 测试通过。

### 原版真实启动

- 原版目录中的 TP 文件保持存在；必要 DLL 在初始化前完成适配，主程序在原保护入口运行前完成恢复。
- 已通过项目 `Session → Bootstrap` 启动链自动登录并进入“战场”大厅。会话观察 260 秒，第 180、240 秒的画面均为大厅；随后通过 `Session` 停止，清理状态为完成。
- 完整进程树记录包含 518 次模块加载事件，未出现已知 TP 模块。6 个原版网页组件进程通过身份验证，主程序及全部子进程退出事件齐全，结束后没有本次进程残留。
- 大厅切换时曾因笼统拒绝子进程而结束会话，已改为网页组件精确身份验证，真实大厅复验通过。
- 249 个客户端 EXE/DLL/SYS 的前后文件集合及 SHA-256 全部一致，包括 `TesSafe.sys`。
- 446 项驱动服务的前后状态一致，未发现 TP 驱动项。当前非提升权限环境启动内核 ETW 跟踪返回访问拒绝，前后快照仍不足以排除瞬时驱动行为；此项保留为验收缺口。
- 修正 `D3DXCreateBuffer` 导入绑定后，用户手动复测确认已成功从匹配进入战局；该次会话日志未记录未处理异常，核对时游戏主进程仍在运行。
- 移动、游戏内正常退出及再次启动仍待验收。

## 实施顺序与通过条件

### 1. 独立恢复游戏映像

输入仅为用户提供的原版客户端及本项目维护的基线规则；输出为内存中的代码、初始化数据、导入符号和入口计划。

- 独立还原原版文件中代码的编码/压缩过程，不调用保护壳完成解包。
- 使用名字或 ordinal 重建导入，在当前进程环境解析地址，不复用捕获中的系统 DLL 地址。
- 核对代码、数据、TLS、重定位和入口关系；不只比较六处补丁签名。
- 用参考映像验证代码恢复结果时，区分加载器修正、运行时数据与已知适配差异，不复制运行状态。
- 拒绝未知版本、越界结构、未解析导入和不完整输出。

**状态：已通过。** 从原版文件独立生成完整映像准备结果，准备期间没有游戏/TP 代码执行；真实进程的写入、回读和入口更新已验证。

### 2. 形成完整的内存适配计划

- 覆盖 TP 加载、初始化、报告，以及取消这些对象后对应的调用和退出路径。
- 调整 EXE 的早期依赖，检查传递导入、TLS、延迟导入和动态加载路径。
- 保留协议和游戏所需 ABI。`TenProxy.dll` 的协议组件与其他初始化职责需要分别处理，整体屏蔽该 DLL 不等于完成适配。
- 需要保留的 DLL，应在其相关初始化执行前完成内存处理；在 `LoadLibrary` 返回后才修改 DLL，不构成前置拦截证明。
- 原版 TP 文件保持存在。此前依赖文件缺失的行为需要逐项消除，裁剪目录下的结果不代表原版目录也能正常运行。

**状态：已实现，启动路径验证通过。** 主程序及必要依赖均有初始化顺序、内存变更和失败处理；后续游戏功能仍需覆盖动态调用路径。

### 3. 接入 Bootstrap

已在 `src/Runtime/launcher/` 内接入专用预启动组件，不改变 NativeBridge ABI。

```text
校验原版文件并准备内存映像
→ 调试线程创建 DEBUG_PROCESS | CREATE_SUSPENDED 进程并纳入本次 Job Object
→ 核对映像身份、地址空间与启动上下文
→ 应用代码、导入、主程序 TP 路径、移动及入口适配
→ 恢复页保护、刷新指令缓存并回读核对
→ 首次 ResumeThread
→ 加载事件设置必要 DLL 入口断点
→ 入口断点处完成 DLL 适配，再放行初始化
→ 注入本地端点
→ 进入游戏
```

启动取消或预启动失败时，结束本次拥有的挂起进程并保留首错；不恢复它去执行原入口。首次恢复后的失败继续使用现有会话清理流程，不影响其他程序或其 TP 实例。

已移除“先运行原保护入口、等待解包签名再适配”的流程；移动适配也在首次恢复前安装。上下文检查要求映像基址、原入口、PEB 关系匹配，并回读验证；当前真实运行验证覆盖本次 Windows 11 x64 宿主。

### 4. 真实客户端验收

在前述准备门全部通过后，使用原版二进制和完整依赖目录进行验证：

1. 适配没有磁盘改写，`TesSafe.sys` 保持原样，没有客户端重建文件落盘。
2. 从进程创建开始采集模块加载和进程创建事件，确认没有 TP 初始化或本次派生的 TP 辅助进程；结束时一次进程快照不足以排除短暂启动。
3. 核对本次运行没有安装或加载相关驱动，不把宿主其他程序的已有状态算成本次行为。
4. 原客户端完成启动、登录、大厅、进图、移动、正常退出及再次启动。
5. 覆盖版本不符、依赖缺失、签名不符、取消和异常退出，验证停止与精确清理。
6. 日志目录或普通日志文件的出现单独做写入者归属判断，不仅凭名称认定 TP 已启动或已移除。

只有这些验收通过，才将“启动游戏时无 TP”列为已实现能力。

## 当前决定

确认并采用纯内存路线，默认启动链已接入，自动进入大厅、匹配后进入战局和整树停止清理已验证。保留原版磁盘内容，不迁移历史捕获或派生客户端文件；继续完成其余游戏内功能和内核驱动事件验收。在这些项目完成前，不将已通过的启动与进图测试等同于完整的“启动游戏时无 TP”验收。

## Windows 机制参考

- [`CREATE_SUSPENDED`](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)：主线程在恢复前保持挂起。
- [DLL 入口调用时序](https://learn.microsoft.com/en-us/windows/win32/dlls/dynamic-link-library-entry-point-function)：静态依赖在进程初始化期间执行入口，运行时加载在 `LoadLibrary` 返回前执行入口。
- [`SEC_IMAGE_NO_EXECUTE`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createfilemappinga)：用于不执行映像的只读检查。
- [调试事件](https://learn.microsoft.com/en-us/windows/win32/debug/debugging-events)：事件处理期间目标线程暂停，创建事件先于用户态执行；退出事件需继续后才完成内核清理。
- [`WaitForDebugEvent`](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-waitfordebugevent)：调试事件由创建目标进程的线程接收，文件事件句柄由调试器关闭。
