# 开源战斗服三模式实施计划

## 目标与边界

按[目标架构](target-architecture.md)统一战斗接口：首期由客户端采样移动和碰撞事实，Rust 裁决战斗结果。
协议兼容后续服务端运动与碰撞模拟，通过权威模式和能力协商接入；本期不实现服务端物理模拟。
现有 C++／Python 宿主与中继作为迁移基础，当前交付状态见文末，不代表 Rust 和 Linux 节点已接通。

| 模式 | 房间管理 | 战斗运行位置 | 账号要求 |
| --- | --- | --- | --- |
| 单机 | 启动器本地平台服务 | 启动器进程内 Rust | 无 |
| LAN | 房主本地平台服务 | 房主启动器进程内 Rust，加入者连接同一战局 | 无 |
| 在线 | Java 服务 | Linux Rust 独立战斗节点 | 登录并在线 |

登录只增加在线匹配，不改变单机或 LAN 能力。普通玩家启动器不注册为在线战斗节点。
Java 创建、分配、管理在线房间，并下发战斗地址和准入信息；原客户端统一连接本机兼容网关，
网关按业务含义选择平台或战斗后端，实时战斗数据不经过 Java。一个房间可以先后创建多场比赛，
各自使用独立 matchId；账号在线状态不强制切换游玩模式。

## 职责

- **客户端/启动器**：各自采样本机玩家的移动、位置和接触事实；一个指定客户端另行采样 AI。
- **Rust 战斗服**：直接采用这些事实，迁移并运行已有 AI、伤害、死亡、复活和结算规则。
  不补建服务端物理模拟或真实性校验；仍检查消息结构、来源归属、去重和房间隔离。
- **Java**：账号、房间、匹配队列、独立节点租约、分配和结果接收，不执行战斗逻辑。
- **统一协议**：区分 roomId、matchId、playerId、actorId、连接 ID，避免用固定原游戏登录身份
  代替平台身份。不同实现共享公共输入输出语义，不依赖彼此的业务模块或内部数据结构。
  原客户端 RID 由网关转换；现有 GameData 字节中继不替代玩家意图、世界观测和权威结果契约。

权威模式在准入及开局时匹配并绑定比赛，局内固定；能力不匹配时拒绝准入，不静默降级。
客户端移动接管、AI 物理驱动和位置同步适配按权威模式启用；后续模式仍需独立完成客户端适配。

LAN 房主负责 AI 采样；在线局由首个完成加载的玩家负责，一局内固定。
采样者退出时以 `aborted` 中止，既不计正常胜负也不迁移采样职责；在线存活玩家返回房间，
LAN 房主退出则关闭房间。普通玩家退出移除其角色，不支持中途加入或断线重连。

首期使用当前洛阳死斗资源、现有支持英雄和主武器，人类与 AI 合计最多 20 个角色。
联机先覆盖地面移动、转向、方向普攻与格挡、受击、死亡、复活、结算；
联机跳跃、蹲伏、冲刺与换武器后续接入，现有单机动作保持不变。

## 实施顺序与验收

### 1. 共用运行时与独立宿主

已有代码：

- `T7R.BattleServer` 无 WPF 控制台，复用原生 `Server` 和 Python 业务，不创建游戏进程。
- 独立 host 句柄、绝对路径配置、显式状态目录、同步停止与 DLL 生命周期。
- 既有启动器会话 ABI 保留；原协议端口只在回环地址监听。
- 战斗模块构建与测试入口，见[宿主说明](../battle-server.md)。

迁移期间的现有宿主继续保持每进程一个 Python owner，多房间通过多个独立进程部署，不引入多解释器。
目标 Rust 核心不依赖 Python、Windows 或原客户端内存接口；Windows 通过 FFI 进程内加载，Linux 使用原生 Rust 宿主。
两端同源、同版本、同业务语义，分别构建平台产物，见 [Rust 迁移计划](rust-runtime-migration.md)。

### 2. 双客户端共享战斗

已有：BattleProtocol v1 有界帧编解码、可靠流传输、TLS 接入检查、节点侧三通道中继、双向角色视图映射，
以及不随玩家连接退出而删除的比赛级计时器。旧局计时器在业务分发前隔离。

待接入：

1. 将连接关联到玩家及本场比赛；每个活动 matchId 一份共享 MatchState，一组比赛/角色计时器。
2. 准入后由本机网关转换原游戏三通道消息，保留本机 RID 1 约定；各接收方映射角色、目标、出生和结算。
3. 世界采样按来源归属汇总：本机人类 + 指定采样端的 AI，每个来源独立批次游标。
4. 帧级保留接触，上报默认 50 ms 一批；即时转发输入，映射比赛时钟与重生代次。
5. 仅采样所有者驱动 AI 物理，其他客户端接受同步位置；原生位置同步屏蔽按所有权区分。
6. 在 Rust 中保持当前已确认的战斗规则，统一伤害、死亡、复活、比分和比赛结束事件。

同一核心先验证进程内与 Linux 网络接入的业务结果一致，并分别覆盖传输顺序、背压和生命周期。

进入后续 Java/UI 大规模接入前，至少两个真实客户端完成同局移动、相互攻击、AI 攻击、
死亡复活、结算和再次开局；验证两端状态一致、接触不重复、旧局事件不污染新局。

### 3. 离线 LAN

- 本地创建、成员列表、准备、开始、离开，不依赖账号或 Java。
- 房主维护房间并启动进程内战局；加入者不另建战局，房主自己也按统一接入语义参与。
- 浏览/开房时启用版本化 UDP 广播发现请求、单播响应，同时支持手工填写地址。
- 覆盖房主断开、普通玩家离开和采样者中止，结束后按房间规则保留成员再次准备。
- 验收断网状态下从发现/加入到结算的完整流程。

### 4. 在线独立节点与 Java 调度

- 节点凭据来自部署配置，与用户登录令牌分离；普通启动器没有节点注册入口。
- 节点注册协议版本、权威模式、地图、规则与资源版本、容量和地址等能力；调度不按实现名称硬编码。
- Linux 节点单进程多局，预留与运行中的比赛均占用容量；各局串行处理事件，不同比赛并行执行。
- 节点内建 TLS，控制面使用 HTTPS；规则与资源来自离线导出的版本化数据包。
- 心跳默认 5 秒，租约 15 秒，过期节点停止新分配。
- FIFO 队列默认等待 10 秒；允许单人开局，均衡阵营并补 AI 至配置容量，最多 20 人。
- 无可用节点时保留排队及取消能力，不分配虚假地址。
- 用户/节点预留与分配事务化；任务确认、开局和结果提交幂等。
- 开局提交已确认的成员和装备等配置快照；实时状态由 Rust 维护，本地或 LAN 结果不直接产生在线奖励。
- 正在进行的战斗不因 Java 暂时断开而停止；完成报告保留并重试。
- 首期持久化战绩，不新增奖励经济规则；节点进程重启不恢复进行中比赛，但保留已落盘的待提交结果。
- Java 新增房间、匹配、节点与结果接口及迁移；沿用既有认证，不改变本地模式。

验收至少两个独立节点的分配、租约过期、取消、重复请求、结果重试及异常回房。

### 5. 交付

- 补齐消息体、错误码、状态转换、接口 OpenAPI、节点部署配置与故障说明。
- 保持公共项目自包含，不包含凭据、内部地址、客户端或非公开算法。
- 模块测试按职责执行；项目级全量测试单独安排。
- 启动器产物与独立节点产物分别组装，不默认改写已有安装目录或发布产物。
- 原客户端程序、DLL 与资源包保持不变；允许按用户操作保存明确支持的用户配置，见[目标架构](target-architecture.md#客户端文件与运行时适配)。

## 当前接入边界

阶段 1 的独立宿主与阶段 2 的帧传输、三通道中继、角色映射和计时器基础已落代码。
新增 C#／Rust 准入消息体、能力匹配及资源数据包工具见[公共契约](../battle-contracts.md)，它们尚未连接实际准入处理器。
三通道中继已验证到宿主的原协议握手，但宿主仍运行原有单客户端状态模型，
还未接入启动器、准入和采样入口。因此目前不开放 LAN/在线按钮，不注册 Java 节点，
也不把两个独立单机实例视为共享战斗。后续按 Rust 迁移进度接入统一契约、共享 MatchState、
网关和采样，再完成 LAN 与 Java 调度；现有 Windows 宿主不等于 Linux 目标节点。
