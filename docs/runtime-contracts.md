# 运行契约

本文面向修改 Desktop、Core、Runtime、Battle 或 BattleRust 的开发者，定义当前模块交互、资源生命周期和持久化格式。用户操作与诊断入口见[使用说明](requirements.md)，组件关系见[架构说明](architecture.md)。

## NativeBridge ABI

导出函数使用 `extern "C" __cdecl`，当前 ABI 版本为 1。参数结构使用 `#pragma pack(push, 8)`，首两个字段固定为 `abiVersion` 和 `structSize`。跨边界只使用固定宽度整数、UTF-8 byte buffer 和不透明 session handle；不传递 STL、异常、`PyObject*` 或内部句柄。

当前库名为 `T7R.NativeBridge.dll`，会话接口使用 `t7r_native_*`，Rust 战斗与网关接口使用 `t7r_gateway_*`（`t7r_battle_ffi.dll`）。ABI 1 保留结构布局、常量值和调用语义，不表示与旧库名或旧导出名称链接兼容；不提供旧接口别名，Desktop、Core、Runtime、Battle 与 Rust DLL 必须整包交付。完整产品名、设置和凭据格式不随技术命名迁移，见[项目命名规范](development.md#项目命名规范)。

[头文件](../src/Runtime/bridge/T7RNativeBridge.h)定义参数和返回值，[导出表](../src/Runtime/bridge/T7RNativeBridge.def)固定以下符号：

| 用途 | 导出函数 |
| --- | --- |
| ABI 与会话 | `t7r_native_get_abi`、`t7r_native_create`、`t7r_native_release` |
| 提交操作 | `t7r_native_submit_check`、`t7r_native_submit_start_gateway`、`t7r_native_submit_start_gateway_profiles`、`t7r_native_submit_stop`、`t7r_native_cancel` |
| 查询结果 | `t7r_native_get_snapshot`、`t7r_native_get_operation`、`t7r_native_get_error`、`t7r_native_read_logs` |
| 输出设备 | `t7r_native_set_output_device` |
| 日志等级 | `t7r_native_set_log_level` |
| 格挡调试 | `t7r_native_set_guard_debug` |
| 画面与声音 | `t7r_native_get_graphics`、`t7r_native_apply_graphics`、`t7r_native_get_audio`、`t7r_native_apply_audio` |

路径输入在提交函数返回前复制，拒绝 NUL、非法 UTF-8、相对路径和超过 32768 bytes 的输入。带名称的启动入口接收 UTF-8 名称，再按客户端 GBK 规则校验；ABI 结构按当前头文件校验。玩家名称由本地平台后端传入 Rust 网关，不通过全局常量或客户端文件传递。

启动器只能使用带网关端口的启动入口：`T7RNativeGatewayStartOptions` 为 56 字节，带战斗配置的 `T7RNativeGatewayProfileStartOptions` 为 72 字节；端口必须非零且互异。未提供 Rust 网关端口的启动请求返回 `INVALID_ARGUMENT`，不会创建旧运行时。跳过动画仍由启动参数 flags 的 bit 0 控制；未知位、错误布局与非零保留字段被拒绝。

输出由调用者提供 buffer；`required` 表示不含终止符的 UTF-8 byte 数，日志 buffer 不足时不消费 cursor。操作提交与完成是不同事件，调用者通过 operation 和 session snapshot 查询结果。

托管侧使用 `LoadLibraryEx` 的绝对包路径和安全搜索 flags，解析固定导出函数。SafeHandle 释放只发起 native cleanup 请求；worker 可能仍在 DLL 内执行，因此桌面进程生命周期内不调用 `FreeLibrary`。

WPF 通过 `INativeBridge` 接口调用运行时，正式装配使用 `NativeBridgeService`。托管测试可注入 fake 实现，不改变 C ABI。

## 生命周期与清理

启动主路径为：

```text
Idle → Checking → StartingRuntime → StartingClient → AdaptingClient → Running
```

- 启动取消进入 `Cancelling`，然后按 `StoppingClient → StoppingRuntime → Idle` 清理。
- 错误先进入 `FailedCleaning`，只有本次创建的客户端、Rust 战局和 listener 都确认清理后才发布 `Failed`。
- 清理仍有错误时保持 `FailedCleaning` 和不可重启状态，只允许再次请求 Stop 重试清理。
- operation 在本轮清理尝试结束后进入终态；托管层可结束当前等待并发起 Stop 重试，但仍以 `cleanupComplete=false` 阻止关闭和再次启动。
- `Running` 不代表客户端已完成游戏内登录或场景加载。

每个 `Session` 只有一个生命周期 worker，操作按提交顺序串行。`cancel` 直接设置当前 operation 的原子取消标志并唤醒 worker，不排在阻塞的 Start 后面。`SafeHandle.ReleaseHandle` 只提交非阻塞释放请求，由 native worker 持有内部引用完成清理。

worker 外层异常也必须记录原始原因并发布 `Failed`／`FailedCleaning`，清理失败另记原因，不用后续清理覆盖首个故障。失败后保留操作循环，仍可请求 Stop 重试清理，不留下接受请求却已退出的 worker。

客户端由 Bootstrap 和 Job Object 管理。`NativeBridgeService` 持有 `OfflineBattleSession`；启动成功后附着采样，结束时先解除采样并停止客户端，再停止 Rust 战局、网关并等待工作线程退出。失败保留所有权供 Stop 重试，不降级到 Python。

显式 Check 先执行 NativeBridge 程序／设备预检，再通过 Rust 的本地资源入口验证并准备缓存；不启动监听、战局或客户端。Start 采用同一 Rust 资源加载入口，读取本地平台配置后将端口和战斗配置交给 NativeBridge。`update.lst` 的版本标识用于资源缓存隔离。

名称资源预检保留训练地图所需的 19 个可用名称及前缀长度约束；实际组队按地图电脑人数检查名称池，并排除玩家同名，名称不足时明确报错，不减少阵容。

资源读取按 GBK 路径表和 44 字节目录记录定位，仅搜索归档末尾 64 MiB；目标条目的存储及解压大小各限 16 MiB。支持 raw 和每块至多 16 KiB 的独立 zlib 流，验证目录范围、路径唯一性和分块数量；歧义目录不选择猜测结果。缓存仅属于当前 Python revision，每次预检清空并重读，revision 退役时清理。检查结束、失败或取消均沿用 RunDirectory 与 Python owner 生命周期，不增加 C ABI 或业务状态字段。

资源错误通过现有错误字符串携带 `[T7R_RESOURCE:<code>]` 标识，区分归档读取、目录非法/歧义、条目缺失、大小超限、解压失败、内容不匹配及覆盖布局。日志保留归档、条目、偏移/长度和异常链；Desktop 将这些错误统一显示为“资源不匹配”，不把详细异常直接放入普通状态区。

游戏主窗口从已校验的客户端对象读取，并核对窗口所属 PID；只有观察到该窗口后才启用关闭检测。窗口被销毁且连续 1 秒未出现同进程、同窗口类的替代主窗口时，自动进入 `StoppingClient`，终止本次 Job 中的残留进程并清理本地服务；最小化、隐藏和短暂窗口重建不触发清理。成功后以 `client-window-closed` 返回 `Idle`，不将主动终止产生的退出码当作崩溃；清理失败仍保持 `FailedCleaning`，清理期间拒绝新的 Start 和 Check。未托管的进程不受影响。

窗口探测抛出异常不等于确认窗口消失：首次失败记录 `WARN`，按既有监测周期重试，连续失败满 5 秒才结束会话；一次成功即重置失败计时。期间继续检查主进程存活，真实进程退出或调试失败不进入这段宽限期。

启动同步由 StartupGate 管理，不依赖窗口标题、弹窗文字或系统代码页。已适配的初始化失败分支不再显示原版启动提示；原初始化成功分支保持不变。首次恢复客户端前，在已校验的服务器选择入口安装断点；命中时校验本次主进程、线程上下文和网络对象，只挂起进入该入口的线程，调试事件循环和其他线程继续运行。Bootstrap 完成端点发布及回读验证后，恢复入口指令并放行所有等待线程；恢复时已排队的断点事件也须回到原入口执行。

门控等待沿用 60 秒超时，分配工作线程沿用 10 秒超时。取消、对象变化、签名不匹配或发布失败时终止本次客户端，不放行空列表选择。停止时先确认调试线程和客户端退出，再清理门控线程句柄。日志按“门控已到达 → 端点发布已验证 → 门控已释放”记录启动进度。该机制只处理启动同步，不改变协议和资源文件的既有编码约定。

端点注入分别分配记录、分组和候选容器，使用客户端原有的对齐分配器并保留其计数；超出 SSO 容量的字符串使用客户端 CRT 的 `operator new` / `operator delete`。分配、释放在客户端运行时执行，避免挂起持有堆锁的线程；发布前重新挂起并核对所有者与原向量。分配返回空指针时回收部分分配并恢复计数，发布回滚后释放未转交的内存，发布成功后由客户端析构释放。调用异常或超时沿用会话终止清理。`VirtualAllocEx` 仅承载临时调用代码与结果，不作为客户端容器或字符串的存储；调用线程退出前不回收其代码页。真实未处理异常仍按失败上报。

客户端首次连接及后续重试均打开 `logic` 通道，因此四条端点记录及其描述字符串统一使用逻辑端口 `ports[1]`，不随选择器奇偶值切换到只发送版本响应的 `login` 端口。保留两个同主机候选、原有连接超时和独立的实例端口，正常启动无需等待一次登录超时后再重试。

MovementOverlay 只在挂起状态安装或撤销四个入口：资源路径别名、XML 缓冲区容量、解析前处理和电脑移动的位置命令过滤。四个签名全部匹配后才写入；局部失败先恢复入口，再释放代码页。只有匹配的移动资源和显式启用的登录片头资源额外预留 4096 字节，变换后的 XML 写入客户端文档自身的内存池，不另持有跨文档的资源缓冲区。

解析前断点由 DebugClient 的原有事件线程处理，限定为本次主进程和已安装的断点地址；线程上下文、文件名、长度及 XML 结构检查失败均沿用会话失败清理。非目标资源走原路径。正常停止先等待调试线程和客户端退出，再清除 overlay 所有权；原 VFS、磁盘资源和其他进程保持不变。

路由行为树复用原移动资源，保留三个生命周期分支及其 GBK `Description`：“进入节点”“退出节点”“执行节点”。客户端按这些标识绑定分支，只有 `ID` 不足以完成解析。每个移动事件入口均检查本地单位与战斗角色；WASD 按下和松开在客户端玩家状态“准备”或“战斗”时交给原树处理，其他输入与事件仍要求“战斗”。不在 `INIT_FINISH` 时切换到未受阶段限制的离线树。原资源路径、相机和碰撞定义保持不变。

确认出战时先发送 `IN_SCENE` 完成选将面板的关闭和角色入场，再在同一批消息中恢复 `READY_PLAY`，通过原生 `MOVE_NOTIFY_ACTIVE(active=0)` 暂停移动控制器，不等待开局倒计时。准备阶段和 `START` 倒计时期间，角色保持原地，仅相机可调整；原树继续更新 WASD 方向与松键状态，业务层仍忽略位移、跳跃和蹲起报告，对象刷新也不激活移动。进入 `GAME` 后发送 `IN_SCENE` 与 `active=1`，由原生控制器恢复已保持的方向；不补发按键或移动命令，不重新创建角色或重置坐标。准备期间已松开或相互抵消的方向键不产生开局位移，准备时间不计入快跑加速。

所有玩家确认出战后，在同一批消息中立即进入 `START`，不再保留额外的 `PREPARE` 等待。当前人机战局的电脑已预选武将，真人完成 `CHOOSE_HERO_REQ → PLAY_REQ` 即满足全员完成条件；只选中武将不算完成，30 秒准备期限到达后仍等待确认，不自动入场或提前消耗最终倒计时。首次确认总是获得完整的 `START` 窗口，不沿用准备阶段的剩余时间；重复确认、过期准备定时器和进入 `GAME` 后的确认均不重置倒计时。

小型战场选择界面仅展示原生团队竞技池中已开放的六张地图：洛阳死斗（1003）、陇上麦田（1030）、栖霞山（1021）、新野（1001）、当阳（6003）、洛州争锋（1034）。客户端在内存中将该显示行的 14 项原始池缩减为这六项，其他模式显示行不变；地图列表、过滤设置和匹配请求共用这个池。排除比例使原标题和确认逻辑均要求至少选择一张。

匹配沿用原 `PROTO_MATCH_PATTERN`：`map_num/map_id[]` 是勾选项，`exclude_map_num/exclude_map_id[]` 是未勾选项，两者互斥。网关校验原数组后只保留可选团队地图，空集、重复项、未知地图或截断请求均拒绝；隐藏的攻城、据点等地图不进入随机池。`prepareMatch` 从勾选项等概率抽取，在返回匹配成功前完成采样解绑、旧战局停止、地图切换、新 epoch 战局创建与重新绑定；沿用原生出生点人数和现有人机击杀计分。

首次启动或旧配置缺少 `selectedMatchMapIds` 时默认全选六张。游戏原始确认逻辑将过滤项写入 `UserData.cfg` 的 `0_<地图ID>` 布尔字段，启动器在运行期间读取已确认项并原子保存到 `settings.json`，停止游戏时再同步一次；关闭选择窗口而未确认不保存草稿。下次启动游戏前从启动器配置恢复这些字段，其他游戏设置保持不变。无效选择和写入失败保留上次有效配置，记录原因并重试；普通启动器设置保存不覆盖游戏刚保存的地图选择。

`START` 窗口为 `5999 ms`（约 6 秒），状态消息和 `GAME` 定时器使用相同起点及期限。原生 HUD 先将剩余毫秒截断为整秒，再等待约 1 秒首次显示数字；窗口略小于 6 秒，避免零延迟边界先显示 `6`，并为正常本机消息处理留出显示 `5 → 4 → 3 → 2 → 1` 的时间。该调整不修改客户端资源；异常长的客户端卡顿仍需实机核对。

每局初始化时将战斗时长写入 `battleClock.durationMs`，来源为内部 context 的 `gameDurationMs`，未指定时取 `contracts.GAME_MS`（当前默认 20 分钟）。有效范围为整数 `1..86400000` ms。进入 `GAME` 时仅一次记录 `battleClock.startedAt`；回合资料、GAME 状态、实例刷新和结束定时器均读取同一记录，截止时间为 `startedAt + durationMs`。准备和开局倒计时不计入战斗时长；本局不接受时长调整，修改配置只影响新局，热更新和重复出战请求不重启计时。

战斗时间结束后进入 `settlement`，冻结玩家和所有电脑的身份、阵营、英雄、击杀、死亡、积分、名次和结果，包括死亡及待复活成员。按阵营总击杀判胜负，同分平局，不加时；各阵营内部按积分降序、击杀降序、死亡升序、RID 升序排列。提前退出记为 `quit`／未完成，保留当前统计但不记胜负；截止时刻及之后退出按正常结束处理。重复结束或退出只生成一次快照和离场流程。

当前战局另有阵营累计击败目标：新局将 `contracts.KILL_TARGET`（本项目约定为 60）保存到 `session.killTarget`，有效范围为整数 `1..2147483647`。顶部目标显示、达标判定和结算快照共用该值；配置变更只影响新局。客户端 `data/propsheet/副本变量.psheet` 定义 `kill_total`，接收后更新 `totalLifeNum`／`ASGetTotalLifeThreshold`；客户端字段已确认，但 60 是本项目采用的规则值，不是从胜利文案解析或已确认的客户端默认数值。

有效致死命中完成计分、死亡通知后，获分阵营累计击败达到目标（`>=`）即以 `kill-target` 原因结算，并明确记录该阵营获胜；包括玩家、友方电脑、敌方电脑完成最后一次击败，以及本地玩家已死亡的情况。同批命中沿用已有接触排序，首次达标后停止余下命中，不再发送观战状态或调度复活。截止时刻及之后仍先执行超时判定，迟到的历史接触不补算；首杀和连杀奖励沿用同一次击败记账，不额外累计。

结束时停止移动、电脑行为、动作、命中和复活定时器，拒绝后续战斗和选将请求。先发送所有成员的最终 `SCORE/UPDATE_EVENT`（原值等于新值，附加个人结果字段 9、阵营内名次字段 51）。超时或击败达标时，先发送 `SI_UPDATE_ROUND_RESULT`（10 / 104）和时长为 5000 ms 的 `END`，由客户端显示原生胜负提示；固定停留 5 秒后，再发送 `SETTLE/UPDATE_MSG`（52 / 1）和 `FINISH_GAME`。停留时长不增加配置项，`round-finish` 定时器保留绝对截止时间，脚本热更新和重复结束事件不重新计时。手动退出不等待；停留期间退出会立即发送已冻结的结果并取消该定时器，不重复结算。

ROUND_RESULT 和 FINISH 使用阵营结果：0 未完成、1 蓝胜、2 红胜、3 平局；SETTLE 和个人 SCORE 使用：0 未完成、1 胜、2 负、3 平局。SETTLE 保持当前等级，奖励、英雄结算和评级数组为空；FINISH 原有四组资格列表不作为 20 人名单使用。

原生帧桥接观察本局 FINISH 的实际消费，在 END 状态下调用原生离场入口，沿用 `SYNC_LOGOUT_REQ/RSP` 打开结算界面，不模拟按键或改写行为树。手动离场和自动离场共用实例级防重入标记，观战、选将或缺少本地角色不阻止结束；函数签名不匹配或原生衔接失败会显式报错。结算快照独立于实例连接保存，关闭实例连接不等于返回大厅；确认 `USER_GROUP/QUIT` 的结算组类型 3 或创建新局后才清除。此桥接随 NativeBridge 安装，需要重启启动器和客户端，单独热更新脚本不生效。

返回大厅时，在 `GameFlow.onEnterLobby` 清空旧的 `enterUI`，打开大厅首页，不再恢复已失效的自定义房间页面；到时结束、击败达标和手动离场共用此落点，结算展示与确认流程保持不变。适配仅作用于 `scripts_game.gfx` 的内存读取结果，校验资源路径、大小和方法字节码，支持分段读取，不修改客户端 VFS 文件。结算持久状态与碰撞查询临时区分开存放，避免帧采样覆盖离场状态。

状态版本 13 迁移旧局时保留已存在的 `round-end` 截止时间，按旧版本公布的时长恢复起点，不重新开始计时、不补造已结束战局的结果。真实客户端的结算画面、回大厅及再次开局验收见[任务清单](planning/task-list.md)。

状态版本 14 增加可选的 `killTarget` 和 `kill-target` 结算原因。旧局缺少目标时继续原有结束规则，不补设目标、不推测历史达标先后；下一局初始化后启用。已有时限、统计和结算快照保持不变，结算仍跨实例连接保留。

滚轮先交给原 UI 处理，再检查客户端已有的相机输入状态；ESC 菜单停用操作时不向游戏继续分发滚轮事件，关闭菜单后恢复。该内存适配只移除滚轮路径中跳过状态检查的分支，不改菜单自身滚动、相机缩放参数或系统输入设置。

### 模型动作

游戏内“防御辅助”（`DefenseAssistMode`）复用客户端原生选向：玩家按下右键时，根据附近对手的攻击方向选择格挡方向；不代替玩家按键，也不新增启动器入口。Runtime 的内存适配移除本地角色初始化时的辅助等级上限，并让原生设置回调同步输入模式与 `is_auto_parry` 标记；开关可在局内切换，关闭后恢复手动选向。目标筛选、距离／朝向约束和服务端格挡命中判定保持原有路径，不修改磁盘客户端或 VFS。此适配随 NativeBridge 加载，更新后需要重启启动器和客户端。

四向攻击和四向招架接收 `cmd=4 / selector=1` 的 11 字节输入，下发现有 `STATE_SYNC_SIMPLE` 动作状态，不生成玩家位移。新建的人机对局另由基础近战模块判定命中与伤害。攻击按“准备 → 蓄势 → 松键出招 → 收招”推进；提前松键仍完成准备阶段，再直接出招。招架准备的固定时长为 0 ms，沿用原定时器调度；准备后停留在 `ParryHold`（223–226）。玩家与电脑松开防御时直接结束动作、回到待机，不下发 `ParryRelease`（227–230），也不再设置收回定时器；准备定时器处理前松键同样直接回待机，并取消原定时器。准备、蓄势与出招阶段的重复按下不重启当前阶段；普通攻击收招允许新攻防输入打断，规则见下文。

攻击与格挡方向以各自角色为准；电脑可使用方向配对选择姿态，结算先检查攻击刀刃扫掠与角色正面查询盒／真实盾面的接触，再检查方向和性能，不额外使用朝向锥。先碰身体仍受伤。成功普通格挡停止攻击窗口，攻击者进入本方向被招架状态（240/246/252/258），防守者仍在原防御时进入成功状态（231–234／盾牌 111），使用带对方 RID 的完整 `STATE_SYNC`。晚到接触不重新启用已经释放的防御。四向基础成功反馈为 0 ms，盾牌使用配置时长；攻击性能高一级时至少 250 ms。反馈后恢复仍保持的防御或有效攻防缓存，被招架方按武器配置时长恢复。左键挡反要求防守方处于 Prepare，覆盖进攻方整个 Strike 的有效接触窗口，不额外限制出招进度；窗口以原生接触起点计时，成功时保留防守方原攻击准备。盒体性能破防只先记录减伤，真正身体命中才扣血，未碰身体不造成受击。性能破防、格挡值耗尽、盾牌耐久耗尽分别结算，参数见[近战攻防规则](combat-rules.md#格挡与受击参数来源)。

已配置先锋使用服务端静态动作表，按实际角色／武器动画时长优先、配置表兜底，不使用跨武器平均值；尚未实现动态攻速属性／加成换算。未配置时长的武器显式报错，未使用先锋配置的电脑继续保留既有默认武器规则。

### 先锋阵容、主武器与空手

PVP 阵容开放四槽，武将来自启用的先锋解锁表，每位武将的近战武器与盾牌单独配置并本地保存。大厅、战场列表与本局选将共享配置；匹配后冻结快照，首次出战和复活均按快照选择。协议、存储格式与验收入口见[先锋阵容与武器配置](loadouts.md)。

沿用客户端 `CMD_HAND`（默认 `~`）和数字槽位键，不轮询物理键或更改键位。前者发送武器命令 `5`、子消息 `1`、槽位 `13`，在上次使用的主武器与默认徒手 `100000` 间切换；数字键请求对应的已配置武器槽位 `1..4`。盾牌槽复用同一请求，由服务端选择本局装备中的单手武器并配盾，选择顺序与无匹配武器时的行为见[先锋阵容与武器配置](loadouts.md#使用)。客户端聊天、菜单与按键配置仍决定是否生成请求。

服务端只在存活、战斗输入开放且无正在执行的动作或受击时接受切换，按顺序发送换武器应答、完整武器使用列表和原生换出状态 `1`，随后回到待机 `2`。主武器和拳头都保留在列表中，仅改变 `is_using`；重复选择当前主武器只应答，不重播动作。死亡／离场取消切换定时器，复活恢复主武器；热更新保留当前装备与动作快照。

换出状态复用客户端 `ChangeWeapon` 动画。已配置先锋的 `state_time_ms` 与服务端切换定时器均采用目标武器的静态时长，动画优先、表值兜底。例如 `1030411` 为 `1000 ms`、徒手为 `833 ms`。客户端将该时长传入 Havok 的 `enforcedDuration`，武器显隐仍由原生 `WeaponVisible` 动画事件控制；切换结束前不接受新的攻击或切换请求。

空手沿用四向攻击、松键出拳及招架流程。已配置先锋按实际徒手动画使用预备 `233 ms`、过程 `400 ms`；上方向收招 `233 ms`，其余方向 `167 ms`。被招架／场景反弹分别取对应拳头参数，不借用主武器时长，也不执行主武器的冲刺攻击。伤害继续使用当前本地近战规则，命中、飘字和击杀消息携带实际攻击武器；晚到接触按出招时保存的武器结算。

拳头没有刀光节点。当前默认徒手的接触采样读取其 `RHand` 挂点实体的原生世界位姿，以资源中的 `0.15 m` 半尺寸生成短段，复用现有逐帧扫掠和角色身体碰撞查询；这是短段近似，不是原服务端的完整拳头体积碰撞。缺失或无效位姿时停止采样，不回退到收起的刀刃。切回主武器恢复刀刃端点，并重置跨武器扫掠历史。

#### 动作输入缓存

- **窗口**：普通攻击的准备、蓄势和出招阶段接受攻击缓存，包括提前松键后仍在准备的阶段；防御按下在攻击准备和蓄势阶段立即打断，在出招阶段缓存。普通攻击收招允许攻击或防御立即打断。防御准备和保持阶段不缓存新的防御方向；松键后可立即接受下一次攻防输入，没有收回阶段。
- **防御打断前摇／蓄力**：普通攻击处于准备或蓄势阶段时，防御按下立即取消当前攻击、清空已有缓存，进入对应方向的招架准备；准备期间即使攻击键已提前松开也可打断。之后松开攻击键不补出被取消的攻击；防御松键直接结束，不补发收回动作。
- **收招打断**：出招结束时已有仍按住的攻防预输入，则直接进入下一动作准备，跳过收招状态及其等待，不插入待机。已进入收招后收到攻击或防御按下，同样立即取消剩余收招及原定时器；松开上一动作的按键不释放另一类新动作。
- **攻击打断防御**：原生按键位 8 表示右键；右键仍按住的攻击意图被忽略，不能覆盖防御或其缓存。右键松开后，原生可以直接发送“左键仍保持”的攻击意图，取消防御准备／保持并进入完整攻击准备。成功反馈期间只缓存该交接，等待反馈结束；匹配的左键松开使缓存失效。
- **硬直预输入**：受击、被招架和地形反弹期间接受四向攻击／防御预输入，但不提前结束反馈。进入这些状态时保留已有且仍按住的缓存；连续受击及反弹中受击也保留，按最后一次恢复期限衔接。招架成功方保持右键时锁定防御方向且不缓存攻击；松右键后的攻击交接或再次按下的防御可缓存，匹配松键使缓存失效，等待反馈结束后衔接。连续格挡保留原有硬直剩余时间，不被后一次较短反馈提前解除。
- **单槽覆盖**：按服务端接收顺序，最后一次有效的四向攻击／防御按下覆盖前一个意图，包括方向；没有多步队列。缓存不发动作包，也不延长或缩短当前阶段定时器。
- **按键保持**：所有攻防预输入均支持提前按住等待衔接，不要求恢复时再次按下；匹配的松键将缓存标记为已释放。衔接时仍按住才执行，否则丢弃，不补放短按，也不恢复被覆盖的旧意图。再次按下可覆盖为新的保持输入；接上的攻击继续完成准备、保持蓄势并等待松键出招。
- **松键隔离**：另一类动作的松键不修改当前缓存；无对应按下的松键不创建缓存。松键同时按原有规则释放当前动作，不被缓存逻辑截断；已经开始的普通攻击提前松键仍完成准备和出招，收招可按上述规则打断。
- **恢复衔接**：受击、被招架、地形反弹恢复，以及完整冲刺结束时，重新检查角色可操作状态；有仍按住的缓存则消费一次，直接进入下一动作准备，不插入待机。受击恢复等待有效位姿时继续保留缓存并处理松键。没有有效缓存时回待机；普通攻击无有效缓存时先正常收招。
- **清空**：死亡、进入新实例、离场、断线及实例失效时丢弃缓存；战局输入关闭时清空动作、缓存和动作定时器。恢复操作后不补放这些旧输入；受击和反弹自身不属于缓存清空条件。

该策略缩短动作间等待，不修改准备／出招时长、伤害窗口或反弹／受击期限，也不作为原服规则的还原结论。实现和回归见 [battle.py](../tests/reference/Business/scripts/battle.py)、[test_battle_buffer.py](../tests/python/test_battle_buffer.py)、[test_battle_recovery.py](../tests/python/test_battle_recovery.py)。

#### 跳跃与蹲伏

Runtime 的内存路由保留原跳跃指令。帧线程观察本地 `GeMovable` 的实际起跳和滞空标记，通过原动画接口在起跳、落地时各发送一次 `Jump`、`EndJump`；指令入队、松开跳跃键和空中方向输入均不重复触发动画。走下平台交给原生坠落动画处理。行为树的 `JUMP_LAND` 分支仅保留原落地音效，不再发送跳跃动画或增加固定落地停顿。蹲伏／起身请求替换为本地 `Crouch`／`EndCrouch` 模型事件。这些分支继续受本地战斗角色和 `GAME` 状态限制，离场结束已启动的跳跃姿态，不修改客户端的重力、碰撞或位置推进。

起跳至落地期间，角色朝向与 WASD 移动方向保持起跳时的状态；原地起跳也不接受空中移动。原生复合指令逐项过滤转向、离线移动和重复起跳，保留位置校正、状态驱动移动与蹲伏。已挂起的起跳请求同样阻止再次起跳，走下平台后的滞空也不接受跳跃。按键缓存仍正常更新，落地时先通过原生转向接口强制同步一次当前相机朝向，再通过原移动指令恢复当前按键对应的方向或停止；落地前停止转动视角也会同步，不补发跳跃。

仅含被拦截输入的跳跃指令组不执行末尾额外的固定物理步；重力与碰撞仍由原生帧循环按经过时间推进，保留未消耗的时间余量。首次起跳与包含位置校正等有效操作的指令组继续使用原物理流程。普通攻击切换阶段不重播 `Jump`，也不提前发送 `EndJump`；攻击清除快跑资格，实际落地后按方向键进入步行或静止状态。

`cmd=2 / selector=52` 的分类 `1` 更新移动快照，分类 `2`、`3` 分别只记录蹲伏、跳跃按键，不覆盖坐标、朝向或 WASD 状态。服务端不为这些输入生成位置回声、固定滞空定时器或跳跃位置积分。可见动画与组合操作仍需实机验收。

### 慢跑、快跑与冲刺攻击

玩家的离线移动参数为起步速度 `3`、快跑速度 `5`，连续前进 `1000 ms` 后进入快跑；允许前进斜移，地面后退、纯侧移、松键，以及蹲伏和非待机战斗动作会清空计时。已进入快跑的跳跃按锁定的起跳方向保留快跑，空中方向输入和松键不改变它；落地后仍前进时不重新等待加速，否则按当前输入停止或步行。尚未进入快跑的跳跃清空计时，落地后重新计算。这些值由 `SprintHookCode.h` 定义，是可调整的离线参数，不是原服速度公式。

普通攻击的准备、蓄力、出招、收招，以及防御的起手、保持、招架成功阶段，移动速度均保持最低档 `3`，同时清除 RUN 提示与快跑计时。持续按住方向键或换方向不会加速；动作结束后，重新连续前进 `1000 ms` 才进入快跑。冲刺攻击直接出招，使用独立的限时位移，不插入静止准备阶段，也不套用普通攻击的慢跑速度。

运行时路由将原直线移动的起步速度改为慢跑值。帧线程只处理本地玩家，调用原速度 setter 改变实际控制器速度，同步八方向的原生移动状态和快跑状态；`MoveDir`、`MoveSpeed` 由原生动画更新统一维护，输入树不再直接覆盖 `MoveDir`。`ENTER_RUNNING/LEAVE_RUNNING` 继续交给原输入树管理 RUN 按键缓存与 Sprint 提示。起跳和滞空期间仅保留已有快跑速度与移动状态，关闭 RUN 冲刺资格及提示，禁止普通、智能攻击模式触发冲刺攻击；落地后恢复保留的资格，不重新等待加速。判定依据原生滞空标记，松开跳跃键不会提前恢复，走下平台同样受限，单纯按住跳跃键但未离地不算滞空。该逻辑不在空中开始新的加速计时，不模拟 Shift、不直接改坐标，独立于角色位姿采样，即使电脑尚未创建也正常工作。实例或实体变化、组件不可用时会丢弃旧计时。

原生移动状态与动画方向不是同一枚举：左前／右前分别为状态 `3`／`9`，快跑为 `11`／`12`，对应 `MoveDir=8`／`2`。映射以本地 WASD 方向为准，左右反向键在各自轴上抵消。

战局内无有效移动方向时保留原停止命令的速度 `0`，不写入慢跑速度；冲刺攻击的限时位移不受松键影响。原地转身继续使用原生 `GeMBCtrlInfantry` 的 `TurnDir` 判定及动画，不另发转身事件或修改朝向。停止转向、恢复移动时，由原生逻辑退出转身动画。

本地离线移动命令执行前，按命令自身的方向补齐原构造器未初始化的移动状态。已进入快跑且仍待机前进时，A、D 切换方向的命令直接保留快跑速度，避免先回落到起步速度、下一帧再恢复而混入步行动画；空中仅保留速度，不恢复 RUN 资格。其他角色、按状态寻向的命令与特殊速度保留原生处理。

实际移动速度与动画混合坐标分别处理。启动时使用服务端静态表中的 `Speed_MoveF_Slow`、`Speed_MoveLR_Slow`、`Speed_MoveB_Slow`、`Speed_MoveF_Sprint` 对应值；它们在离线导出时从实际角色／武器绑定核对，是动画混合参考值，不是物理速度或硬切换阈值。原生 `MoveSpeed` 写入处将地面待机移动、防御准备及保持映射到所选慢走档；只有原快跑计时已完成的待机前进才使用快跑档。低速保留原速度下限后的比例混合，上一帧残留速度不超过当前档位；防御松键后的重新计时期间不混入快跑档。原生动画缓存与 setter 保持一致，不额外发送动画事件，不修改控制器速度、坐标或计时。前进斜移沿用横移的慢走参考值，后退斜移沿用后退参考值；静止、蹲伏、空中、其他战斗动作及其他角色保留原生逻辑。绑定或资源不可用时记录诊断并保留原生选档，不借用其他武器参数。

普通攻击模式下，提示出现后新按下 Shift，经原 `CMD_EGE` 与武器消息表生成 `700250`。提前按住 Shift 不会在提示出现时自动出招；智能攻击模式继续使用原“快跑＋鼠标攻击”入口。业务层检查 RUN 及攻击键位，拒绝动作中重复／缓存冲刺。前进条件由运行时读取独立的移动按键缓存检查，不要求战斗消息同时携带 W 键位。接受请求时直接同步出招状态 `439`，不发送 `438` 准备状态，也不通过零延时定时器过渡；完整过程结束后衔接仍按住的攻防缓存，否则回到 `2`，不等待松键，不额外插入 `440` 收招。当前不实现主动提前取消；受击、反弹、死亡和离场仍可打断。

冲刺参数来自服务端 [combat_profile_data.py](../tests/reference/Business/scripts/combat_profile_data.py) 静态表，生产由 Rust 冻结数据 → `ClientCombatProfiles` → NativeBridge → Bootstrap 提供给战局和原生位移适配；预检和游戏运行不读取客户端动作表或动画文件。离线导出时按武将／武器的实际动画绑定选取有效动画时长，配置表兜底；武器类别、位移、接触参数与原始伤害 ID 按 `(组 6, 武器类别, 动作 13, 模式 2)` 精确选表，与原生冲刺状态 `438/439/440/443` 一致，动作 `32` 的战技参数不参与冲刺。没有冲刺参数的武器不启用冲刺。原生参数表按武将 ID 与当前武器 ID 查询，不借用上一武将的移动参数。

以武器 `1030411`、类别 `32` 为例，当前静态值如下：

| 参数 | 资源字段 | 当前值 |
| --- | --- | --- |
| 过程时长 | `DashAttack` 动画；表值 `1200 ms` 兜底 | `1333 ms` |
| 位移时长 | `[移动时间]` | `500 ms` |
| 位移初速度 | `[移动初速度]` | `4000`，按千分比换算为 `4.0` |
| 碰撞窗口 | `[碰撞时间]开始`、`[碰撞时间]结束` | `540～720 ms`，含两端 |
| 反弹恢复 | `DashAttackParryed` 裁剪后动画；状态 `443` 表值 `933 ms` 兜底 | `800 ms` |

状态 `439` 的同步报文将 `state_time_ms` 设为完整过程时长；客户端换算为秒后经 `BattleStateDuration → DashAttack.enforcedDuration` 同比缩放动画。该字段不是已播放时间，`state_change_ms` 才表示状态开始时刻。状态 `443` 同样同步完整反弹时长，其动画与恢复定时器使用相同数值；其他状态保持原行为。暂不引入最终攻速、Buff 或其他时长修正，各逻辑时间轴的修正比例统一为 `1`。

离线导出对动画裁剪、播放倍率和分支进行核对，取最近整数毫秒；绑定不明确、循环或分支时长不唯一时使用表值，并将原因写入 `timingSources`。碰撞窗口结束超过动画时长时截到动画结束，原值／新值写入 `windowAdjustments`。位移时长和速度不跟随缩放。时长须在 `1～65535 ms`，窗口必须有效且不超出过程；不合格的静态配置阻止发布。已有防御 `0 ms`、按住维持及复活等待不变，地图等其他必需资源仍执行原预检。

原生位移仍调用原向前移动／停止命令，方向向前、加速度为零，不直接改坐标。计时使用 `GeFightable` 的 `sequence / phaseTick`，与原生碰撞记录共用动作时钟；首次观察延迟、按键改变或松键均不重新开始位移。到达配置的位移截止点后保持零速，动画继续到完整过程结束。相同状态的新序号仍视为新动作。结束或受击／反弹打断时恢复当前方向键；无方向键则停止移动，重新从慢跑计时。离场清除快跑提示及计时。

每次动作和碰撞记录保存配置及窗口快照，晚到的命中记录按原动作序号和原窗口结算。碰撞范围仍采用刀光端点扫掠及原生 Havok 身体／场景碰撞，不使用固定距离扇形；窗口开启后随原生快照检测，不等待 AI 轮询。同一次出招对每个敌人最多结算一次；冲刺与普通攻击共用零强化属性和倍率公式，见[近战伤害](loadouts.md#近战伤害)。冲刺仍配对下招架；被招架或撞地形进入 `443` 并停止后续命中。电脑可招架但不主动冲刺，双方死亡／复活规则不变。

资源或移动适配变更后须重新构建并重启 Runtime 和客户端，Python 热更新不重载启动配置；缺少动作配置快照的旧冲刺状态要求重启。回归用例包含精确选表、动画回退、资源错误、禁用行为、窗口两端、动作快照、晚到碰撞及合成 x86 位移时钟。实机验收检查慢跑／快跑、Shift 直接出招、位移截止后原地播完、过程结束衔接和反弹恢复；主动提前取消不在当前范围。跨武将、跨武器的动作与移动参数通过各自资源绑定选择。

### 战局聊天与动作输入

准备结束进入 `GAME` 时，Runtime 通过原 `UIResetFocus` 清理准备界面遗留的文本焦点，并同步原鼠标模式消息，恢复鼠标控制相机，不再依赖手动开关聊天。此交接每次进入战斗只执行一次，不持续抢占菜单焦点。

Esc／设置和结算界面的原生自由光标请求优先于聊天适配：保留文本焦点和输入法，保持自由光标，不在失焦或关闭时回放旧的聊天光标状态。判定使用原生光标请求计数和相机模式的自由光标标记，不把窗口激活状态当作菜单状态。倒计时结束或复活时若菜单仍开着，也不重置其焦点或捕获鼠标；结算界面即使保留 `GAME` 角色状态，也由原界面管理光标。窗口处于后台时不主动捕获鼠标，回到前台后仍以当前界面请求为准。

战局中未编辑聊天时，Runtime 解除游戏窗口的输入法关联，Shift 继续走原玩家动作映射。按 Enter 打开聊天并获得文本焦点后，恢复输入法，Shift 用于输入法切换，文字键不触发战斗动作；鼠标仍保持捕获并控制相机。退出聊天后恢复动作输入及进入聊天前的鼠标模式；若聊天前主动释放了光标，关闭聊天后恢复自由光标。

切换依据原 UI 的真实文本焦点状态，不将 IME 订阅方的残留字节视为聊天焦点，不轮询 Enter、不模拟 Shift，也不修改系统输入法配置。输入法选词和发送仍由原聊天界面处理，持续编辑期间不反复关联输入法或重置组合文本。离开战局时恢复本适配移除的输入法关联，鼠标交回大厅逻辑管理。

该适配随 NativeBridge 构建、在客户端启动时安装，需重新构建 NativeBridge 并重启客户端。合成 x86 测试覆盖准备结束的残留焦点／相机状态、IME 与 UI 焦点不一致、聊天时的相机控制和键盘隔离、前台菜单／结算光标优先级、菜单跨开局和复活、前后台切换、预先自由的光标、离场重进、窗口／服务更换及寄存器保护。实机检查：准备结束后直接转动相机、使用 Shift；Enter 打开聊天后输入中文、选词、切换输入法，同时移动鼠标转动相机；反复用 Esc 打开和关闭面板、编辑设置字段，并在聊天、倒计时或复活期间打开面板；在菜单及结算界面切换前后台，检查光标自由移动、按钮可点击；返回大厅检查鼠标和输入法正常。

### 电脑玩家位姿采样

Rust 战局按开局步兵点建立 1 名玩家和 19 名电脑。`BattleWorker` 以 100 ms AI 脉冲及独立动作／复活／结算期限驱动同一状态所有者；原生位姿与接触由 `BattleSnapshotIngress` 映射时间和 RID 后提交。公开业务身份、输入时间与发布回滚见 [战斗契约](battle-contracts.md)。原生指针和句柄不跨 Rust 业务边界；没有 Python 状态版本迁移或热更新。

采样复用已有帧线程入口，但有独立邮箱。原游戏线程检查本地角色状态、实例、最多 20 个 RID 与组件/控制器，在同一帧调用原位置和朝向 getter，前后核对实例 epoch，最后发布完成标记。战局运行时主机以 5 ms 等待间隔轮询，画面、声音及生命周期监控保持 50 ms。位姿和刀刃在每个游戏帧独立采样，不等待主机请求或业务处理。主机请求只冻结一批位姿、地形结果与累计接触；响应区保持不变，实时区继续采样。`sampledAt` 取实际游戏帧时间，再转换到服务端时钟域。非有限位姿或缺少实体只关闭该项就绪标记，超时与实例失效关闭整批就绪标记，业务层再次检查 250 ms 新鲜度与当前实例。AI 预判与招架方向只使用该朝向，不回退到按键上报缓存或电脑计划朝向；原地转身无需等待移动上报。

世界快照与逐个电脑的移动采样分开提交。移动采样先校验来源、批次及角色实体／位姿／采样时间的一致性；校验通过但处理时已超过 250 ms 的样本不更新 AI 移动与脱困状态，也不终止战局。250 ms 边界仍有效，后续新快照继续正常处理；不一致的数据仍返回错误。

位姿只读取本次启动器拥有的客户端。内存代码先校验原函数签名，保存寄存器和 FPU/SSE 状态；客户端退出后清除邮箱，不写磁盘二进制。地图标识、出生／复活参考点和导航拓扑由 Rust 内嵌 `resources/data/battle-baseline-v1.json`（训练地图）和 `match-maps-v1.json`（12 张匹配地图）维护，运行时不读取客户端地图归档。`clientDirectory` 仍是可执行文件目录，供先锋目录、电脑名称等独立资源读取使用。电脑自主动作和移动分别以 RID `2..20` 为目标，不接管玩家输入；玩家受击时只推进自己的动作序号并取消被打断的动作，仍按住的预输入保留至恢复后衔接。

角色间接触、滑动、重叠恢复与位置推进由原生 Havok 角色控制器逐帧处理，同阵营也参与碰撞。VISION 的 `filter_group` 和电脑 MOVE 的 `system_group` 均使用角色 RID；不同角色不共用非零组号，同一角色的附属碰撞体保留同组自过滤。原角色胶囊及碰撞层矩阵不变。

电脑仍使用 `MOVE / selector=38` 的原生速度、方向、状态、激活与分组命令。Runtime 仅在该接收链且目标为 RID `2..20` 时，跳过 `PosCommand` 入队并通过原生析构释放它；TDR 的位置字段保留，但不写回模型或控制器。其他接收链、玩家命令及出生 VISION 定位不受该入口影响。Rust 按采样位置更新路径进度，只提出绕行意图，不再积分电脑坐标或发送玩家拉回、电脑小步分离包；单独转向使用不含坐标的 `selector=56`。升级需配套构建 NativeBridge 和 Rust 并重启客户端。

`botWorld.actors[rid].terrain` 保留 `forward` 和最近目标的 `target` 结果，`targetTerrain` 按目标 RID 字符串保存独立的接触线结果；未就绪项不发布。结果字段为 `ready`、`hit`、`material`、`position`、`normal`、`direction`，共用位姿的采样时间及实例 epoch。每个角色查询面前 2.2 米，以及上一批位姿选出的全部正面敌人（水平 2.2 米内、高差不超过 1 米、左右各 60°）；每批最多 60 条前向射线；敌我接触线按实际阵容枚举，30 对 30 时上限为 1800 条有向接触线。下一游戏帧用双方新坐标执行查询，仅供 AI 接近与威胁预判；缺少本目标结果时不借用最近目标的结果，也不将这些接触线作为伤害依据。玩家为 RID 1，双方人数取地图原生点数；敌我关系由当前战局的 RID／阵营绑定确定，不依赖固定分段，目标掩码使用 64 位覆盖 RID 1–60。Runtime 在游戏帧中校验 `MapInfo` 的静态场景碰撞刚体和战斗世界，对原生 Havok 查询增加仅接收该刚体的收集器，并读取命中形状材质；导航世界、角色和独立动态物体不混入地形结果。无场景数据与查询失败区别于有效的无命中，指针不跨帧或进入战斗业务状态。

`botWorld.blades[rid]` 是独立的原生刀刃接触快照：`ready`、`spanMs`（0～100）、`length`、`base`、`tip`、`contacts`。端点取自当前武器 `GeSwooshable` 绑定的原生刀光节点（B 为刀根，A 为刀尖），读取实时世界坐标，不依赖刀光开关。长度取两点距离，支持范围 0.01～8 米。每个接触复用地形字段，并含 `targetId`（0 为场景）、`time`（本段时间比例）、`along`（刀根到刀尖比例），两者均在 0～1。场景阻挡面与地面分别保留最早的一条接触，均使用 `targetId=0`；角色仍按 RID 各保留一条。

刀刃扫掠在原游戏帧线程查询相邻采样之间的运动线与前后截面，沿刀刃采样间隔约 4 厘米，复用 Havok 世界查询与角色原生骨骼伤害碰撞体。它是分段线性近似，不是精确扫掠体或历史身体回放；采样间隔只取决于实际游戏帧，不受主机读取和 AI 决策周期控制；同一个时钟刻度中的多个游戏帧也保留连续扫掠。收集器只接收本帧确认的场景／存活角色刚体根节点；忽略自身、尸体、触发器与无关动态物体。更换武器、角色实体或出招序号、实例变化、缺失端点、原生帧间隔超过 100 ms 或端点跳变超过 4 米均重置历史。查询完成后才发布，原生指针不离开客户端邮箱。

基础近战在出招窗口消费有效刀刃接触。普通攻击的 `0/0` 表窗口覆盖完整出招阶段（已配置先锋的空手为 `400 ms`）；显式窗口与冲刺窗口使用静态表中已截到动作结束的值。接触窗口不改变攻击范围。

普通主手使用角色正面的查询用 OBB，盾牌继续使用已激活副手 `GeWeapon` 的 `GeHavokPhysicable` 原生根形状；两者均核对物理世界。盒体尺寸、偏移和启用条件见[近战规则](combat-rules.md#武器拦截挡反与盾牌)，不注册物理刚体。主手与盾面按实际武器 ID 区分，盒体另带 `guardVolume` 来源；保持和成功反馈可连续拦截，攻击 Prepare 交给 Rust 检查挡反窗口，攻击 Hold 不收集为防御。每个攻击者分开保存 `MAX_WORLD_ACTORS` 个身体槽和同数防御槽，以及场景阻挡／地面两槽。`defenceWeaponId=0` 表示身体或场景，非零表示实际防御武器；无效的防御接触直接忽略，不当作身体伤害。完全相同时间、刀刃位置和目标的接触以防御武器优先。该内部布局变更要求配套 Runtime 重启，不改变启动器 C ABI。

`botWorld.contactJournal` 按批次发布累计接触（最多 8192 条），包含 `damageEvidenceVersion=2`、`batchId`、`throughAt`、`frames`、`dropped` 与 `events`。每条接触记录实际发生时间、原生出刀状态／序号／起点、双方实体标识、接触时位姿及防守状态，以及原始 `bodyIndex`、`region`、`sourceVelocity`、`targetVelocity`、`weaponVelocity`、`velocityReady`、`airborne`、`targetAirborne` 与 `defenceWeaponId`；速度单位为米／秒，腾空取 `GeMovable` 原标记，不携带原生指针。队列满时显式记录溢出，不静默覆盖。结算按 `occurredAt`、`along`、RID 排序，以原生出刀起点计算原有窗口；回调晚到、业务已进入收招不抹去窗口内接触。中断按发生时间截断，实例变化和复活隔离旧接触。新契约要求配套 Runtime；已有队列缺少证据版本时明确报错。单帧结算路径仍用于合成接触测试；不再检查固定距离／高度／攻击朝向扇形，也不从缺失刀刃数据回退到旧算法。每刀对每个目标最多结算一次身体伤害；友军身体不扣血但影响后续伤害，友军武器不消耗穿透名额，敌人受武器顺劈次数限制，已接触 RID 随状态保存。反馈采用原生接触点、方向与法线，不用身体中心代理重算。玩家与电脑的所有攻击均不受地面／坡面阻挡：单位法线 `abs(normal.z) >= 0.5`（坡度不超过 60°），接触平面投影到接触时攻击者脚下 XY 后，高度不超过脚下位置加 0.1 米。射线穿入／穿出导致的法线翻转不影响判定，头顶障碍仍阻挡。地面接触不中断攻击，通过场景目标为 0、`ignore_hurt=1` 的 `HIT_POINT_NOTIFY` 保留原有材质撞击声，每刀最多一次，播放标记随挥击状态保存，重复投递与热更新不重播。原生收集器将地面与阻挡面分槽归并，避免声音接触遮蔽墙壁；业务队列与单帧路径采用相同规则，角色身体不按地面处理。成功格挡或撞到墙壁、障碍物侧面等其余阻挡面立即停止本刀后续接触。撞阻挡面取消攻击窗口和原阶段，保留仍按住的预输入供反弹结束后衔接，普通攻击使用 `466/468/467/469`、冲刺使用 `443` 反弹状态，以及场景目标为 0、带实际法线／材质的 `HIT_POINT_NOTIFY`，不伤害被遮挡目标。玩家血量使用隐式本地目标的 `BATTLE/DATA_UPDATE_NOTIFY`，电脑血量使用显式目标的 `ATTR/ATTR_UPDATE`；受击使用带攻击者目标 RID 的完整 `STATE_SYNC`。双方初始血量 100，最低为 0；伤害、蓄势、护甲、部位、速度、特性及盾牌规则见[近战伤害](loadouts.md#近战伤害)。头部命中携带原协议 `IS_CRITICAL=5`，友军衰减携带 `DECAY_DELTA_HP=6`、攻击性能按 F 处理，`ignore_hurt` 由护甲打断条件决定；飘字只显示实际扣血，死亡和计分仍只执行一次。

格挡值与盾牌耐久独立。格挡值变动经 `BATTLE / selector 48` 的单个 float 通知本地 HUD；自然恢复按原生接触队列的 `throughAt` 水位推进，投递延迟不凭空增加恢复。性能破防使用状态 `360`／击倒 `362`，资源耗尽使用 `598`，普通击倒使用 `40`；持续时间和护甲门槛见近战规则。移动锁定与动作恢复分开计时；玩家通过原 `MOVE_NOTIFY_ACTIVE` 暂停／恢复，电脑锁定时停止位移；死亡／新生命不恢复旧锁定。业务状态版本 `19` 拒绝旧已初始化战局热迁移。

电脑归零后取消行动，先发送 `INSTANCE/KILL_EVENT`（10 / 6）、适用的 `SCORE/STAT_MSG`（12 / 2）连杀公告及 `SCORE/UPDATE_EVENT`（12 / 1）计分板更新，再同步死亡状态 `42` 和显式 RID 的 `DEAD_NOTIFY`；后者会解除死者 RID 映射，不能早于 HUD 消息处理。5000 ms 后选择己方复活参考点附近的可用战场地面，以相同 RID 的 `VISION DEL/ADD` 恢复客户端生命状态与 100 血量。训练地图保留蓝方 14 个、红方 12 个参考点，匹配地图使用各自适配后的己方参考点；快照过期、无合格候选或候选全被占用时每 50 ms 重试。

玩家致死命中使用同一击杀计分、死亡动作和 `DEAD_NOTIFY`，并更新 ACTOR 状态 `9`（VIEW）。客户端原生行为树负责死亡相机延迟、左右键循环观战队友及自由转动；当前主角死亡相机延迟为 3000 ms，观战对象死亡后的切换延迟为 2000 ms，不改写客户端资源。致死 8000 ms 后发送 ACTOR 状态 `7`（WAIT_BORN），沿用原生选将及 `CHOOSE_HERO_REQ → PLAY_REQ` 确认链；倒计时内或存活时不接受复活选将，不以旧选将结果自动出战。

复活沿用匹配时冻结的先锋阵容与武器配置，直接选择地图中启用、己方、`is_revive` 且匹配兵种的配置点；不使用电脑的战场地面投影规则。点被占用、资源或快照未就绪时每 50 ms 重试，不回退到死亡位置或其他兵种点。确认后以同一 RID 重建实体、恢复 100 血量并发送 ACTOR 状态 `6`（IN_SCENE）；新实体位姿确认前关闭业务输入与命中。观战和选将期间继续采样其他存活角色并推进电脑战斗；死亡玩家的 VISION 刷新不重建尸体或重置相机计时。玩家生命周期和期限可随热更新保留，离场取消定时器，新局重置。

个人计分板更新包含时间、角色 RID、`stat_msg_id` 和四个计分项：击杀（类型 2、44）、死亡（类型 3）、战场积分（类型 1），每项为 `type/src_value/dst_value` 三个 int32；`dst_value` 为绝对总值。`stat_msg_id` 通常为 0，整场首杀的胜者更新使用 `730000`，由原客户端触发首杀表现，刷新快照不重放。客户端模式 7、10、18 只采用类型 44，其余模式只采用类型 2；两种击杀字段发送相同总值，不重复累计。每次实际击杀只记一次：胜者击杀加 1、积分加 100，死者死亡加 1，分别发送双方更新，且早于 `DEAD_NOTIFY`。多杀逐个登记，助攻、救助不变。`kills`、`deaths`、`battlePoints` 随角色状态保存，复活不清零，成员重导入用原值等于新值的快照恢复显示；新局清零。旧状态缺少字段时按零兼容，已有计数保留，不从连杀反推累计击杀。协议上限为非负 int32，达到上限后饱和，不回绕。

战场屠夫身份由单次生命的 `killStreak >= 10` 判定；死亡清零前若满足条件，向胜者发送 `SCORE/STAT_MSG` 的 `730140`（次数 1）屠夫终结者公告，不替换胜者自身适用的连杀公告。首杀标记 `firstBloodAwarded` 为战局级布尔值，缺省兼容旧状态，已有击杀／死亡／连杀记录时不补发首杀；新局重置，复活和热更新保留。原生协议及资源映射见[击杀公告说明](computer-player.md#电脑死亡与复活)。

顶部阵营击杀数由 `SCRIPT/UPDATE_ITEM_MSG`（23 / 1）独立更新，body 为大端 `uint16 selector + uint64 svr_time + uint64 mid + int32 item_num`，随后是 `int32 key + int64 value` 的变量项。当前实例 MID 为 1；`blue` 的名称键为 `7346418`，`red` 为 `206159`，值为绝对累计击杀数。新局同时发送 `kill_total`，名称键 `0xA0034FCD` 按有符号 int32 编码为 `-1610395699`，值为本局击败目标，三项共 58 字节；旧局没有目标时保留两项 46 字节。键不是变量表序号 1、2、7。初始计分、每次击败和实例刷新均同步同一目标。客户端将阵营计数更新到 `selfKillNum/enemyKillNum`，而 `INSTANCE/COMBAT_POINT_NOTIFY`（10 / 107）更新的是另一组 `selfScore/enemyScore` 字段。

每次击杀结算后按阵营汇总所有成员的 `kills`，包括死亡及待复活成员，蓝方为 camp 1、红方为 camp 2；不累加个人战场积分，也不另存一份阵营计数。实例资料刷新和成员名单重导入后补发绝对总值，新局随个人计数归零。虽然变量值以 int64 编码，客户端击杀字段仍按非负 int32 上限饱和，避免读取低 32 位时回绕。

战场复活选点使用当前所选地图的导航，适用于训练地图及全部 12 张匹配地图。以己方配置复活点为参考，限制水平 XY 半径 32 米，选取与己方开局战场区域连通、留有角色半径空间的导航地面点；Z 使用地面高度加 0.2 米，不使用参考高台高度。候选必须有可通行路径且不被角色占用；没有合格候选时不扩大范围、不回退到配置点。新实体位姿确认后直接恢复普通 AI，不创建高台离开或固定返场路线。已在执行的旧高台衔接状态继续支持热更新，后续复活改用新选点规则。地图标识、血量、死亡状态、复活期限与反馈定时器随热更新保留，离场取消，新对局重置。详细范围、资源配置和实机步骤见[电脑玩家说明](computer-player.md)。

### 输入法子进程兼容

每次启动读取 Windows IMM 与用户/系统 TSF 注册信息，覆盖 x86、x64 注册表视图并处理 WOW64 模块路径。仅当主游戏或已验证游戏组件实际加载注册模块时，才启用本次会话的兼容模式；模块卸载不撤销，下次启动重新判定。注册信息读取或路径解析失败时记录 `WARN` 并保持原有严格子进程策略，不使用不完整快照。

输入法身份判定仅依据 IMM/TSF 注册模块，不增加签名、证书、文件哈希或安装目录校验。兼容模式允许本次进程树中的其他未知子进程，但不将这些进程标记为“已验证输入法程序”；它们必须属于本次 Job。已知游戏组件即使在兼容模式下也必须匹配原路径及 SHA-256，同名但不匹配时仍结束会话。

兼容子进程不执行游戏专用 DLL 适配，已知禁用模块检查仍适用于所有进程。兼容子进程非零退出或发生未处理异常时记录 `WARN`；异常只终止该子进程，不影响游戏会话。调试、终止或清理失败仍走会话失败清理。停止、取消或主进程退出时回收本次 Job 内的全部后代，不处理启动前已存在的外部进程。日志记录进程角色、PID、模块名和注册来源，不记录完整个人路径或命令行。

已完成路径、哈希、Job 归属及初始化适配校验的 WebHelper 是可独立失败的网页辅助组件：未处理异常只结束自身并记录 `WARN`，主游戏继续。其他已验证组件默认仍是关键组件；身份不匹配、适配失败、禁用模块、调试事件或清理失败均保留整场失败策略。

### 跳过启动动画

点击“启动游戏”时固定本次 `SkipStartupAnimation` 值。启用后，复用解析前入口，仅处理 `../data/btree/流程_登陆.btree`：校验 `43506` 选择节点及其两个完整分支，将发送 `GeASEventTitleMovieDone` 的跳过分支移至加载 `TITLEMOVIE` 的播放分支之前。客户端继续执行原有登录完成逻辑，其他节点、GBK 编码和空白字节保持不变。实现见 [StartupAnimation.cpp](../src/Runtime/launcher/StartupAnimation.cpp)。

关闭时不拦截该资源；启动中或运行中切换选项只影响下次启动。新手关片头、地图加载、VFS 优先级和磁盘资源均不变；目标 XML 结构不匹配时终止本次启动并沿用会话清理。

## 游戏配置文件与模式切换

输出设备是启动偏好，独立于游戏画面配置，保存在 `settings.json` 的 `outputDeviceId`：空字符串表示系统默认，否则使用 D3D9 `DeviceIdentifier` 的 GUID（D 格式），不保存可能变化的枚举序号。设备列表仅包含 HAL PS/VS 3.0 达标的适配器；已保存但未检测到的设备保留并提示，不代选其他设备。

`t7r_native_set_output_device` 复制 16 字节 GUID，全零表示默认；后续 Check/Start 命令各自固定该标识，操作执行期间拒绝修改。启动时重新解析设备序号并检查能力。显式选择时，在客户端首次恢复执行前校验并安装渲染初始化与分辨率枚举入口，使两者使用同一适配器；默认选择保持原入口不变。首次画面快照就绪时回读渲染器设备序号和 GUID，确认一致后才报告已确认，磁盘二进制不变。

游戏未运行时，“设置 → 游戏设置”直接读取客户端 `Bin/../Data/UserData/UserData.cfg`，保存后下次启动游戏生效。此文件为 `PropertySheet Version="100"` 格式，兼容原客户端允许的 `6_1001` 等数字开头字段，保存时保留原字段名，不要求用户删除键位配置。画面与声音值位于 `Record Name="Config"`，缺少记录值时沿用 `Header` 默认值；旧配置缺少 `Swoosh` 时视为 `0`，保存画面设置时补齐类型声明。解析仍禁止 DTD 和外部实体。

本地玩家出刀时使用客户端原生蓝色刀光预设 `PVP赵云专用`。帧线程只控制原生组件的配置与启停，节点采样、拖尾绘制和 LOD 仍由客户端处理；蓄力、收招、招架、受击、死亡、观战及换下武器时关闭。`Swoosh` 的 `0`（全部开启）和 `1`（仅开启本人）显示玩家刀光，`2`（关闭）隐藏，战局内切换即时生效；其他角色原有效果不变，刀刃命中计算不受显示开关影响。

离线保存只更新对应组的字段，保留其他设置、记录、注释、XML 编码和 BOM；兼容 GBK、UTF-8 及 UTF-16 大小端，无编码声明的 UTF-16 文件也保持原编码。不修改 `PlayerConfig.cfg` 或其他用户配置。使用同目录临时文件、`Flush(true)` 和原子替换，旧文件保留为 `UserData.cfg.bak`。保存前回读并比较该组原值，发现冲突时同步文件中的最新值，不覆盖外部修改。文件缺失、格式无效或写入失败会在设置组内提示，不以默认值覆盖损坏文件。

离线时每秒回读文件，未变化的配置不影响编辑草稿；外部修改只更新变化的设置组。游戏启动或结束期间暂停编辑，运行后仅使用内存同步，不因内存尚未就绪或同步失败而回退写文件。游戏退出并完成清理后重新读取文件。切换模式或客户端目录不自动提交未保存草稿；目录尚在编辑、验证中时禁用保存。检测到同目录中非本次启动器托管的游戏进程时暂停文件编辑，不附加其他进程。

## 画面设置同步

“设置 → 游戏设置”提供分辨率、显示模式、画质、视野距离、视野雾、死亡物理效果、垂直同步、帧数限制和刀光。编辑只改变草稿，点击“保存设置”才写入当前数据源。“初始化设置”也需要保存，“撤销修改”恢复配置文件或运行中游戏的当前值。

分辨率选项与游戏一样枚举输出设备的 D3D9 32-bit 显示模式，合并不同刷新率的重复尺寸并保留枚举顺序，不使用固定预设列表。未运行时使用当前选择，运行时使用本次启动固定的设备；运行中修改输出设备只影响下次启动。进入文件编辑或运行时同步、离线切换输出设备时重新枚举；当前配置中的自定义分辨率仍可显示，读取失败时仅保留当前值并提示，不影响其他画面选项的保存。

`t7r_native_get_graphics` 返回独立的 64-byte 快照（ABI 1），`t7r_native_apply_graphics` 接收同结构的值和期望 `revision`，仅排队而不阻塞 UI。状态为 `Unavailable / Ready / Applying / Failed / Conflict`。内存模式下，游戏未就绪、停止中或同步失败时禁用编辑；只操作本次启动器拥有的进程。

启动前安装帧线程邮箱，配置查询及应用均在原游戏线程执行并保留寄存器、FPU/SSE 状态。应用使用原画面设置处理函数，由游戏更新渲染状态并保存当前用户配置，不修改客户端磁盘二进制。`ConfigLevel` 与五档画质反向映射，帧数限制对应 60 / 200；启用垂直同步时沿用游戏的同步限帧行为。

显示模式读取渲染器已生效的模式和实际窗口样式，而非仅依赖配置中的 `FullScreen`。从全屏切回窗口时，先在游戏线程恢复窗口，再执行原设置流程；只有渲染模式、窗口样式及恢复状态均确认成功后才报告已应用。设备未就绪或切换失败时不以配置保存成功代替应用确认。普通窗口内设置修改和声音设置保存不主动恢复窗口。

原生工作线程以 50 ms 间隔推进读请求，启动器每 250 ms 读取缓存。游戏内保存后自动回读，不触发反向写入；新值到来时替换未保存草稿并提示。提交时核对 revision，游戏线程执行前再次比较当前原始配置；发生冲突只回读新值，不覆盖游戏。画面设置保存在游戏配置中，不在 `settings.json` 再保存一份或启动时自动覆盖。

## 声音设置同步

“设置 → 游戏设置”中的声音设置提供背景音乐、游戏音效的独立开关和 0–100% 音量。关闭声音保留原音量，不修改 Windows 系统音量。编辑、保存、初始化、撤销和冲突处理与画面设置一致；两类设置各自保存，不互相覆盖。

`t7r_native_get_audio` / `t7r_native_apply_audio` 使用独立的 40-byte 快照（ABI 1），音量以 0–1 浮点数传递，静音标记为 0 / 1。声音邮箱复用原游戏帧线程入口，但有独立请求、revision 和失败状态。调用原音乐、音效设置函数更新声音引擎，再以仅声音变更标记调用原保存函数；不触发分辨率或显示模式变更。

声音资源目录取自所选客户端的 `Data/Audio/Wwise/Windows`。启动前检查目录、系统代码页无损转换及 ANSI Bank 枚举；通过后，在客户端首次恢复执行前统一安装五处内存补丁：Wwise 宽字符媒体路径、初始化和场景切换的 ANSI 扫描路径及两处字符串长度。长度使用实际 ANSI 字节数和完整宽度指令，不受 127 字节限制；保留原有路径长度检查及原枚举器限制。路径存储为只读，长度跳板为可执行只读，均保留至客户端退出，磁盘客户端不变。

资源缺失、路径编码或枚举预检失败时，仅记录 `Audio resource paths unavailable; original audio behavior retained` 日志，跳过整套路径补丁并继续原客户端声音行为；不弹窗、不强制静音、不修改用户声音设置。补丁签名或安装失败则终止该次客户端启动，避免运行部分适配状态。成功日志为 `Audio absolute resource paths installed; sites=5`，附带代码页和路径长度。

Bank 的选择、加载和卸载沿用原客户端场景逻辑，不按实例额外加载固定 Bank 名单。验收应结合已有 Wwise 加载、卸载、播放日志及实际听感，覆盖大厅、加载、战斗、结算、返回大厅再进图和不同实例模式；非零播放 ID 不等于已实际发声。

回读使用游戏当前声音状态，因此游戏内调整音量或静音时即可同步，不必等到保存。启动器不在 `settings.json` 保存第二份声音配置，也不自动回写游戏内变更。

## 服务就绪与端口

Rust `Gateway::start` 在 `127.0.0.1:0` 绑定三个 listener，完成资源准备和 IO worker 启动后返回实际端口。托管层只在成功绑定后提交 NativeBridge 启动，客户端不接收端口 0。

登录通道认证后等待 1 秒发送版本响应；逻辑通道等待 1 秒发送登录响应，再等待 1 秒发送登录同步。Rust 保留既有通知顺序，实例初始化和倒计时独立处理。

客户端左上角 Ping 使用最近一次已完成的应用层心跳往返耗时，包含本地通信、服务端排队与业务处理，以及客户端收包调度，不取平均值或底层连接延迟。沿用客户端原有心跳周期、时间戳回显和整数毫秒换算；小于 1 ms 可显示 `0 ms`，新的零耗时采样不会被旧值替代，尚未返回的请求不覆盖已完成采样。该显示适配随 NativeBridge 在客户端启动时安装，需重新构建 NativeBridge 并重启客户端。定向验证：`T7R.NativeTests.exe --ping-tests`、`python -m pytest -q tests/python/test_heartbeat.py`。

## 战场上下文与业务桥接

NativeBridge 的 `BattleSnapshotIngress` 将原生采样转换为公共证据，经 `BattleGatewaySink` 提交 Rust。资源、战局时间校验、原生接触和公开状态发布契约见 [battle-contracts.md](battle-contracts.md)。C# 平台请求邮箱负责身份、阵容和装备；战斗规则不再执行 Python 事件回调。

称号归属仍由账号平台确认：C# 先提交原生说明表，NativeBridge 在帧线程应用完成后回报 epoch／requestId；随后 C# 将同一目录发布给 Rust。Rust 编码 USER_INFO 查询和推送，保留一个待确认佩戴请求；确认、10 秒超时、账号 epoch 变化或连接断开后清理。普通更新不抢先报告佩戴成功。

## 日志与保留规则

用户数据根目录为 `%LOCALAPPDATA%/T7-Rekindle`。托管日志位于 `logs/desktop.log`，原生诊断位于 `logs/native.log`；Rust 资源缓存位于 `battle-cache/`，本地战斗配置位于 `player-profile.json`。

启动器与原生运行时统一采用以下四级日志。默认最低等级为 `INFO`，只输出所选等级及更严重的记录；界面使用中文等级，文件使用英文等级，正文与来源不做翻译。

| 等级 / 界面名称 | 输出点分类 |
| --- | --- |
| `DEBUG` / 调试 | 客户端模块与子进程跟踪、内存适配细节、首次机会异常、音频设备与服务探测、音频快照和应用请求；Journal 的 `C2S`、`S2C`、`COMMIT`；业务诊断快照、电脑档案/决策/目标/脱困/出生区移动、复活选点、接触/命中/格挡/地形计算及正常移动计时校正 |
| `INFO` / 信息 | 检查、启动门控、会话运行、正常退出、主动取消、输入法兼容启用、输出设备检查、画面/声音设置应用成功；正常连接关闭与脚本检查/热更新/回滚成功；初始化等待、队伍生成、击杀、死亡、复活和结算 |
| `WARN` / 警告 | 账号心跳/推送重试及远端注销/下线未完成；客户端版本探测降级、输入法注册表读取失败、兼容子进程异常、画面/声音同步未确认或中断；异常连接关闭、脚本修订清理失败、Journal 队列丢弃；未知业务命令、接触溢出、移动定时器修复/丢帧、玩家复活资源暂不可用 |
| `ERROR` / 错误 | 启动器操作、设置读写、账号登录/本地状态保存、原生初始化失败；主进程未处理异常及其故障上下文、非正常退出、业务事件或 socket 初始化失败、日志文件写入失败、运行记录清理失败 |

`t7r_native_set_log_level(session, level)` 使用 `DEBUG=0`、`INFO=1`、`WARN=2`、`ERROR=3`，拒绝其他值和已关闭会话。调用可在检查、启动或运行期间执行；会话与 Journal 诊断副本共享线程安全阈值。ABI 版本和现有结构布局不变。旧诊断文本的 `WARNING` 仍可读取，新输出统一为 `WARN`。

Rust 原协议诊断可通过 `T7R_BATTLE_CAPTURE_PATH` 显式启用；默认不记录 wire／采样正文。旧 Python transition、Journal 和 COMMIT 分段日志仅保留在 `tests/reference` 对照测试，不再是产品运行契约。

采样录制与 `.gateway.log` 都是可选诊断。创建、队列容量或写盘失败时告警并停用对应诊断，不停止游戏；录制禁用不在采样线程等待写盘，结束时仅报告录制不完整。已生成的录制不得声明完整覆盖；路径限制、独占新建和不覆盖已有文件保持不变。真实接触证据丢失仍由战斗接入校验拒绝，不因停用诊断而放行。

## 设置格式

设置文件是 `%LOCALAPPDATA%/T7-Rekindle/settings.json`，备份为同目录的 `settings.json.bak`。JSON 使用 camelCase 字段名：

| 字段 | 默认值 | 含义与约束 |
| --- | --- | --- |
| `schemaVersion` | `1` | 当前仅接受版本 1 |
| `clientDirectory` | `""` | 已验证的客户端目录；非空时须为完整路径，UTF-8 编码不超过 32768 bytes，不含 NUL 或换行 |
| `playerName` | `"新玩家"` | 玩家名称；非空时按 GBK 名称规则校验，最多 31 字节 |
| `windowWidth` | `1200` | schema 接受 480–4096；窗口实际尺寸由当前工作区决定 |
| `windowHeight` | `900` | schema 接受 320–4096；小工作区不强制此下限 |
| `darkTheme` | `false` | 启动器设置中的浅色／深色偏好，保存后立即生效；系统高对比度优先，关闭后恢复该偏好 |
| `minimizeToTray` | `false` | 检测到本次受管理游戏进程后收起到托盘 |
| `startWithWindows` | `false` | 当前用户登录时打开启动器，不启动游戏；对应 HKCU Run 中的 `T7-Rekindle` 项 |
| `skipStartupAnimation` | `false` | 下次启动时跳过登录片头；不跳过新手关过场或地图加载 |
| `outputDeviceId` | `""` | 系统默认输出设备；显式选择保存 D3D9 DeviceIdentifier 的 GUID，下一次启动生效 |
| `logLevel` | `"INFO"` | 最低输出日志等级，仅接受 `DEBUG`、`INFO`、`WARN`、`ERROR`；保存后立即作用于界面和两份诊断日志 |
| `showGuardDebug` | `false` | 显示客户端格挡盒、实际攻击扫掠与接触点，保存后即时切换；不改变战斗规则 |
| `selectedMatchMapIds` | `[1003,1030,1021,1001,6003,1034]` | 已确认的团队地图选择，至少一项、无重复，仅接受上述六张；旧配置缺失时全选 |
| `updateChannel` | `"stable"` | 更新订阅渠道，仅接受 `stable`（正式版）或 `preview`（预览版），与当前构建身份独立 |

首次启动或旧设置缺少名称字段时使用“新玩家”，已保存的名称保持不变。设置允许空目录和空名称，开始游戏前仍须完成验证。旧配置缺少启动偏好字段时使用 `false`。设置读取拒绝未知字段和 JSON 尾随内容。

旧配置缺少 `logLevel` 时使用 `INFO`；无效等级沿用配置校验和备份恢复流程，不提升 schema 版本。修改等级时同步原生与托管阈值，再原子保存；失败则恢复先前阈值和选项并显示错误。回退到尚不识别 `logLevel` 的旧版启动器时，该版本可能拒绝此配置。

`showGuardDebug` 缺失时为 `false`，不提升 schema。启动器“游戏设置 → 启动器设置 → 显示格挡调试几何”经 `SetGuardDebug(bool)`／`t7r_native_set_guard_debug(session, enabled)` 即时应用再保存；保存失败回滚，其他设置保存保留该值。原生入口仅接受 `0/1`，不改变 ABI 结构；Desktop 与 NativeBridge 配套交付。

绘制复用采样的盒体和实际扫掠线段：灰色为未启用，青色为保持／成功反馈，黄色为攻击 Prepare；接触点短暂显示，不用颜色宣称服务端裁决。D3D9 在 UI 相机覆盖前使用场景相机，开启深度测试、关闭深度写入，恢复渲染状态与 stream 0；不跨设备 Reset 持有渲染资源。未就绪世界或过期采样不绘制，采样／绘制故障只停用该诊断，不影响战斗裁决。真实接触证据采样故障仍沿用战局错误处理。


旧配置缺少 `updateChannel` 时，读取同目录的 `update-settings.json`，无效时尝试其 `.bak`，将渠道与其余设置一起原子保存到 `settings.json`；两份旧渠道配置均无效时使用正式渠道并提示。已有 `updateChannel` 的主配置或恢复备份优先，不再导入旧渠道文件。迁移不删除旧文件，完成后不再维护它们；迁移写入失败会提示并保留原文件，后续读取重试。主配置和备份都损坏时，不以迁移为由覆盖原文件。回退到尚不识别 `updateChannel` 的旧版启动器时，该版本可能拒绝此配置。

写入使用同目录临时文件、`Flush(true)` 和原子替换；替换已有文件时保留上一份为备份。读取损坏配置时保留原文件、尝试备份并反馈警告；两者均不可用时加载默认设置。具体实现见 [UserSettings / SettingsSchema](../src/Core/Settings.cs) 和 [SettingsService](../src/Desktop/Services/SettingsService.cs)。

### 预览准入

预览渠道须持有绑定本机和当前 Windows 用户的 7 天离线签名授权，独立存入同目录 `preview-access.json`，由 DPAPI `CurrentUser` 保护；不增加普通设置字段或提升 schema。授权格式、公钥配置与签发见[预览渠道离线授权](preview-access.md)。

新门禁策略首次运行，在任何更新请求之前将已有预览订阅重置为正式；主配置、备份恢复与旧渠道文件迁移均经过此步骤，其他设置保持不变。保存正式渠道后才记录迁移完成；失败时内存使用正式并提示，下次启动重试，损坏主配置与备份不被迁移覆盖。后续启动仅在有效授权存在时保留预览，配置或备份中的 `preview` 不作为授权依据。

到期停止新的预览操作，已有检查、下载和安装允许收尾后切回正式；切换失败不恢复预览准入。安装版与便携版共享当前用户的授权存储，不同 Windows 用户分别申请。普通设置保存、回退备份及 schema 重置不触碰授权文件；旧版启动器不识别此门禁。

### 回退设置契约

新程序包声明 `rollbackProtocol: 1` 和 `settingsSchemaVersion`。打包验证设置 schema 与 `SettingsSchema.CurrentVersion`、安装器中的 `RollbackSettingsSchemaVersion` 一致。后续增加旧版不接受的字段或改变字段含义时，必须提升设置 schema 并实现对应的正常升级迁移；不得仅依据版本号猜测兼容性。

回退安装器等待启动器退出后，将 `settings.json`、`settings.json.bak`、`update-settings.json`、`update-settings.json.bak` 中实际存在的文件复制到 `%LOCALAPPDATA%\T7-Rekindle\settings-backups\<operationId>.backup`。`backup.ini` 记录原始文件存在状态、本项目 HKCU Run 登录启动项及安装目录。备份失败停止安装；已有备份不覆盖、不自动删除。

schema 相同时保留设置；不同时，程序安装成功后才清除上述四份配置并写入目标 schema 与选中的 `updateChannel`，其余字段由目标版本默认值初始化，同时移除本项目登录启动项。普通安装和普通更新不执行此重置。重置失败尝试恢复全部配置与启动项，显示备份位置并停止自动启动；该流程不提供程序目录的原子恢复。

手动恢复设置时，先确认 `backup.ini` 的 `installation.complete=1`，安装与备份 schema 兼容的启动器并完全退出，再按文件存在记录将原本存在的文件复制回设置目录，移除原本不存在的同名文件。登录启动项可在启动器设置中重新启用；不要将高版本设置直接恢复给不兼容的旧版。备份仅保存在本机，不随发布上传。

T7R 安装包在文件安装及上述设置处理成功后、自动启动前，仅清理安装根目录的 `T7.Core.dll`、`T7.NativeBridge.dll`。不使用通配符或递归删除，不触及其他文件、游戏目录及用户数据；文件缺失视为成功。同名目录、占用或删除失败会保留明确诊断、返回退出码 `20` 并停止自动启动；不回滚已安装的新文件或已成功保存的设置，解决问题后可重新安装重试。退出等待、备份或设置处理失败时不执行旧库清理。

回退到使用旧库名的版本时，由旧安装包重新提供所需 DLL；旧安装器可能保留未被加载的 `T7R` 库，这不构成旧接口兼容层，也不要求改写历史安装包。

## 大厅本地公告

大厅的 `bannerView` 和 `bbsView` 加载产品目录中的 `news/index.html`，分别显示横幅和新闻列表。页面包含示例公告、指南、虚构战报与可点击的详情，不依赖外部网站。编辑该文件并重新打包即可更新内容；运行中的会话缓存页面，修改后需重新启动游戏。

每次会话在 `127.0.0.1` 动态分配临时 HTTP 端口，只提供公告页面，不开放目录浏览。Bootstrap 在客户端首次恢复主线程前安装界面初始化、构造与导航适配，只替换这两个网页区域的地址，原客户端文件保持原样。支付、弹窗与活动区域沿用原逻辑。经过身份验证的网页辅助进程会等待 CEF 浏览器创建完成后再处理地址，避免异步初始化期间访问空指针。停止或启动失败时关闭公告服务，远程钩子内存随拥有的客户端进程退出释放。

客户端通过固定的 128 字节字段传递网页地址，因此使用短的本机 HTTP 地址。合成 x86 测试覆盖首次地址、后续导航、内联与堆存储的区域名、其他区域隔离、浏览器就绪前后的地址更新、标志位、寄存器、栈平衡与 FPU/SSE 保存；打包测试检查公告页复制及清单登记。

### 实现流程

1. `RuntimeAssets.targets` 将 `src/Desktop/Resources/News/index.html` 复制到产品目录，打包清单登记该文件。页面通过 `#banner` 与 `#news` 区分横幅和列表，文章使用同页 hash 切换，没有外部资源请求。
2. `Session::executeStart` 在内部 `Config` 中设置页面路径。`Bootstrap` 启动 `LobbyNews`，读取并缓存不超过 256 KiB 的页面，在回环地址分配临时端口。服务只响应 `GET /` 与 `GET /index.html`，其他路径返回 404；响应声明 UTF-8、内容长度和禁止缓存。
3. 客户端恢复主线程前，检查三个补丁点的原始指令，并分配 x86 远程代码页。构造调用点 RVA `0x3EF79D` 根据精确消息名 `bbsMessage`、`bannerMessage` 设置对应 URL 和初始 URL 修订号。导航入口 RVA `0x3EF870` 同样替换这两个区域的地址，支持区域名的内联与堆存储。
4. 界面加载调用点 RVA `0x3FDC06` 包装原始加载函数；仅在返回成功时调用原有网页初始化处理器 RVA `0x3FF860`。包装保存原函数返回值、通用寄存器和 FPU/SSE 状态，随后返回原调用流程。
5. `DebugClient` 在网页辅助进程的创建事件中，先验证路径、文件哈希及所属 Job，再执行 `ChildImageRule::prepare`。辅助进程 RVA `0x5826` 的适配检查浏览器指针；尚未创建时跳过 URL 更新，不消费修订号，创建后继续原有更新逻辑。
6. 远程写入复用内存回读、页面保护和指令缓存刷新机制。启动失败由现有会话清理终止拥有的进程树；已经可能被补丁引用的代码页保持到进程退出。停止会话后结束 HTTP 工作线程、关闭监听套接字并释放 Winsock 引用。

这些 RVA、对象布局和签名只适用于当前受支持的客户端基线，不作为其他版本的通用网页注入接口。公告文件缺失、服务创建失败或补丁安装失败目前会使启动失败，不做公告降级。

### 验证边界

已完成横幅与列表的实机显示检查，以及本地 HTTP、合成 x86 地址替换、浏览器就绪保护和打包测试。文章点击与返回尚未通过实机验收；页面实现了切换逻辑，但游戏的鼠标事件传递仍需验证。新增子进程预处理回调抛异常时的完整进程树清理，也需要补充针对性回归测试。
