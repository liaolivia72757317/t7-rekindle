# 创建 Git Commit

按逻辑边界创建内容聚焦、信息准确的本地提交；适合独立交付的改动主动拆为多个 commit，单一完整改动保留为一个 commit。默认只创建新 commit，不自动 push、打 Tag、创建 Release 或改写历史。

## 1. 明确操作与范围

- 用户明确要求“提交代码”“创建 commit”时，才执行暂存和提交；仅要求生成、建议或审阅提交信息时保持只读。
- 区分用户指定的文件、已暂存改动、当前任务改动与全部改动，不把“提交一下”自动解释为提交整个工作区。
- 范围已明确时直接执行，不重复确认。纳入范围或拆分边界存在实质歧义时，先展示差异摘要并询问，得到回答后再修改暂存区；独立改动的边界清晰时，按第 3 步主动规划多个 commit。
- 保留范围外的工作区和暂存区内容。不要用 `stash`、`reset`、`restore` 或切换分支来清理现场，也不要用临时索引绕开尚未明确的范围问题。

## 2. 检查仓库与实际差异

读取仓库及目标文件所在目录的 `AGENTS.md`，在仓库根目录执行检查。PowerShell 下逐条检查原生命令的 `$LASTEXITCODE`，不只依赖 `$ErrorActionPreference`；除已解释的预期退出码外，失败即停止。

```powershell
git rev-parse --show-toplevel
git status --short --branch
git diff --stat
git diff --cached --stat
git ls-files --others --exclude-standard
```

- 记录当前分支和 HEAD；已有提交时查看近期提交格式，尚无提交时按初始提交处理。detached HEAD 或正在进行 merge、rebase、cherry-pick 等操作时，说明状态并先确认处理方式；发现未解决冲突时报告并停止，等待用户决定。
- 阅读候选文件的 `git diff`、`git diff --cached` 和必要上下文。未跟踪文件不出现在普通 diff 中，需要单独读取；删除和重命名也要纳入范围检查。
- 检查候选内容是否含凭据、内部地址、个人绝对路径、其他工程信息、日志或构建产物。发现不适合公开的内容时指出文件和问题类型，不回显敏感值；先处理再提交。
- 依据 [开发与交付](../../../docs/development.md#2-构建与测试) 选择与本次改动相关的检查，复用针对相同内容的有效结果。文档或技能变更不要求完整产品构建；测试失败或出现警告时先报告并处理，不为提交而跳过检查或修改无关代码。
- 同一文件还有未暂存改动时，工作区测试结果不等于暂存快照已验证；如实记录验证范围和未执行的检查。

## 3. 规划适当的提交拆分

- 以可独立审阅、验证和回滚的逻辑变化为单位，将不同功能、无关修复或独立维护事项拆开，不默认把所有改动合成一个 commit。
- 同一功能或修复所需的实现、测试和文档通常放在同一提交；不要机械按文件、目录或文件类型拆分，也不要为增加数量制造琐碎提交。
- 按依赖顺序安排提交。每个中间提交应在此前提交的基础上保持构建和相关测试可用，不依赖后续提交才能完整工作；紧密耦合、拆开即失效的改动保留在一起。
- 例如，缺陷修复和对应回归测试属于同一提交，与其无关的 CI 调整另建提交。单一完整改动无需强拆；用户明确要求单个提交或指定分组时尊重其选择。
- 形成有序计划，列出每组的目的、文件或片段范围及依赖关系。同一文件跨组时按片段划分，避免提前纳入后续组的内容。
- 已有暂存内容跨多个计划提交时，先确认是否已明确允许重新分组；尚未允许则询问，已明确要求拆分这些暂存内容则不重复确认。重分时保留范围外的暂存内容和原有未暂存差异。

## 4. 生成各组提交信息

为计划中的每个 commit 分别生成信息，仅描述该组将提交的实际内容，不用其他组、范围外改动、未来计划或未验证的效果充数。

- 标题使用 `<type>: <description>`。类型限于 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf`、`ci`，按实际目的选择。
- 描述默认使用简洁中文，保留技术标识的原文，说明具体变化，避免“更新代码”等空泛标题。
- 需要补充背景、行为影响或兼容性约束时，在空行后增加正文；简单变更只写标题。不把测试未执行写成测试通过。
- 用户提供信息时优先保留；与实际差异或仓库约定冲突时先询问，不擅自改写其意图。

仅请求提交信息时，按计划顺序输出各组草稿及对应范围后结束。请求实际提交时，先展示有序提交计划、各组信息、验证结果和“仅本地提交”；用户已明确要求提交且范围清晰时继续，不增加重复确认。

## 5. 逐组精确暂存并复核

按计划顺序对每组执行第 5、6 步，完成并验证当前组后再处理下一组，不一次暂存所有计划提交。仅在当前组范围清晰且现有暂存区全部属于该组时继续；若包含其他组或范围外的暂存内容，先按第 1、3 步明确处理方式。`$paths` 为当前组中需整文件纳入提交的仓库相对路径数组；使用 literal pathspec，避免文件名中的通配符被解释为其他路径。

```powershell
git --literal-pathspecs add -- $paths
if ($LASTEXITCODE -ne 0) { throw '暂存失败，请检查当前暂存区' }
```

只提交现有暂存内容时跳过 `git add`。部分暂存文件保持原有边界；仅选择片段时使用可复核的补丁或交互式暂存并检查结果，不用整文件 `git add` 混入其余改动。不使用 `git add .`、无路径的 `git add -A` 或 `git commit -a` 扩大范围。

提交前重新检查完整暂存区，而非只检查目标路径：

```powershell
git diff --cached --check
if ($LASTEXITCODE -ne 0) { throw '暂存内容检查失败' }

git diff --cached --stat
if ($LASTEXITCODE -ne 0) { throw '读取暂存摘要失败' }

git diff --cached
if ($LASTEXITCODE -ne 0) { throw '读取暂存差异失败' }
```

确认暂存区非空，文件、片段和提交信息仅对应当前组，分支与 HEAD 未意外变化。发现额外改动时停止并询问，不自动取消用户已有的暂存内容。没有可提交变化时报告并核对剩余计划，不创建空提交。

## 6. 创建并验证当前组提交

`$message` 为当前组的完整提交信息。使用无 BOM 的 UTF-8 临时文件传递中文和多行正文：

```powershell
$messageFile = [System.IO.Path]::GetTempFileName()
try {
    [System.IO.File]::WriteAllText($messageFile, $message, [System.Text.UTF8Encoding]::new($false))
    git commit --file "$messageFile"
    if ($LASTEXITCODE -ne 0) { throw '提交失败，请复查 HEAD、暂存区和 hook 输出' }
}
finally {
    Remove-Item -LiteralPath $messageFile -ErrorAction Stop
}

git log -1 --format='%H%n%B'
if ($LASTEXITCODE -ne 0) { throw '读取提交信息失败' }

git show --stat --oneline HEAD
if ($LASTEXITCODE -ne 0) { throw '读取提交摘要失败' }

git status --short --branch
if ($LASTEXITCODE -ne 0) { throw '读取提交后状态失败' }
```

- 保留仓库现有的作者、签名和 hook 设置。身份缺失、签名或 hook 失败时先报告，不自动修改 Git 配置、使用 `--no-verify` 或关闭签名。
- hook 修改文件或命令中断时，先核实 HEAD 是否已更新及剩余差异，再决定后续动作；不盲目重试、不自动追加或 amend 提交。
- 对照提交前的 HEAD、完整暂存差异和信息，核对新提交的父提交、实际补丁与正文；初始提交没有父提交。核实范围外改动仍保留，验证异常时保留现场并报告，不自动回滚或重写历史。
- 当前组验证成功后记录 SHA，以该提交作为下一组的 HEAD 基线。任一组提交或验证失败时停止后续组，报告已完成提交和剩余计划，不撤销已成功的提交。

## 7. 报告结果

按实际创建顺序简要列出每个 commit 的 SHA、标题、改动摘要和检查结果，说明剩余未提交改动，并注明尚未推送。部分完成时区分已完成与未执行的组；仅请求起草时明确这是提交信息草稿。

推送是单独操作：只有用户明确要求，且远端与目标分支清晰后才执行；有歧义先询问，不使用强推或附带标签推送。创建本地 commit 不代表 CI 或发布成功。
